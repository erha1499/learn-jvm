# 单元八 执行引擎：解释器、JIT 与逃逸分析

本单元的核心：热点代码才值得编译。JVM 先用**解释器**把程序跑起来，发现哪段代码跑得多，再交给 **JIT 编译器**编译成机器码，并在编译时做大量优化。

**学完这个单元，你能：**

- 说清 JVM 为什么同时需要解释器和 JIT 编译器，并用实验看到“越跑越快”。
- 看懂 `-XX:+PrintCompilation` 的输出，说出分层编译的几层分别做什么。
- 说出方法内联和逃逸分析做了什么，用实验证明“对象不一定在堆上分配”。

单元一讲到字节码由解释器逐条执行，当时留了个尾巴：不加 `-Xint` 时，递归能叠的层数每次都不一样。本单元把执行引擎讲完：先看解释器和 JIT 的分工（8.1），再看 JVM 怎么判断热点、分几层编译（8.2），最后看 JIT 最重要的两项优化：方法内联和逃逸分析（8.3）。

## 8.1 解释器与 JIT

- **解释器**：读一条字节码，执行一条。不需要准备，程序马上就能跑，但每次执行都要重新“翻译”，慢。
- **JIT（Just-In-Time）编译器**：把一整个方法编译成本地机器码，之后直接执行机器码，快。但编译本身要花时间和内存。

好比同声传译和书面翻译：解释器是同声传译，说一句翻一句，马上就能开讲；JIT 是把反复要讲的稿子提前翻成书面稿，翻的时候要花工夫，之后照着念就快了。只有反复讲的稿子才值得翻。

`examples/JitWarmup.java` 把同一个计算方法分 8 批执行，每批调用 200 次，记录每批的耗时。JDK 17 实测：

| 批次 | 默认（解释器 + JIT） | `-Xint`（只用解释器） |
| --- | --- | --- |
| 第 1 批 | 879 µs | 1355 µs |
| 第 2 批 | 555 µs | 1444 µs |
| 第 3 批 | 262 µs | 1385 µs |
| 第 4 批 | 194 µs | 1374 µs |
| 第 5 到 8 批 | 193 到 197 µs | 1364 到 1414 µs |

- 默认模式下，前三批一批比一批快，第四批起稳定在 194µs 左右：方法被 JIT 编译了。
- 只用解释器时，每批都在 1400µs 左右，是编译后的 7 倍。

**为什么不一开始就把所有代码都编译好？** 一是启动慢：程序里大部分代码只执行一两次，编译它们得不偿失。二是 JIT 能利用**运行时信息**：哪个分支常走、某个接口实际上只有一个实现类，据此做出比静态编译更激进的优化。追求极速启动的场景（比如 Serverless），可以用 GraalVM 的 native-image 提前编译成可执行文件。

## 8.2 热点探测与分层编译

**怎么判断热点**：JVM 给每个方法维护两个计数器。

- **方法调用计数器**：方法被调用一次加一。
- **回边计数器**：循环每跳回开头一次加一。一个方法可能只调用一次，但里面的循环转了几百万圈，它也是热点。

计数超过阈值，就提交一个编译任务。编译在后台线程里进行，编译完成前继续解释执行，不会卡住业务。如果热点是一个正在运行的长循环，JVM 能在循环中途把它切换到编译好的版本，叫 **OSR**（On-Stack Replacement，栈上替换）。

**分层编译**：HotSpot 有两个 JIT 编译器。

| 层级 | 谁来执行 | 特点 |
| --- | --- | --- |
| 0 | 解释器 | 顺便收集运行信息 |
| 1 到 3 | C1 编译器 | 编译快，做简单优化；第 3 层会插入代码收集更详细的运行信息 |
| 4 | C2 编译器 | 编译慢，根据收集到的信息做激进优化，生成的代码最快 |

常见的路线是 0 → 3 → 4：先用 C1 快速编一个能跑的版本，同时收集信息；够热了再交给 C2 精雕细琢。`-XX:+PrintCompilation` 会打印每一次编译，JitWarmup 里 `work` 方法的编译记录（JDK 17 实测）：

```text
     15    7 %     3       JitWarmup::work @ 4 (29 bytes)
     15    8       3       JitWarmup::work (29 bytes)
     15    9 %     4       JitWarmup::work @ 4 (29 bytes)
     16    7 %     3       JitWarmup::work @ 4 (29 bytes)   made not entrant
     28  106       4       JitWarmup::work (29 bytes)
     29    8       3       JitWarmup::work (29 bytes)   made not entrant
```

- 各列依次是：程序启动后的毫秒数、编译任务编号、标记（`%` 表示 OSR）、层级、方法名。`@ 4` 是 OSR 切入点，字节码偏移量 4，正是循环开头。
- 第 15ms：循环里的回边计数先到阈值，C1 编了一个 OSR 版本（第 3 层），紧接着又编了整个方法（第 3 层）和 C2 的 OSR 版本（第 4 层）。
- 第 28ms：C2 编好了整个方法（第 4 层），旧的第 3 层版本被标记为 `made not entrant`，不再使用。

C2 的激进优化建立在假设上，比如“这个接口只有一个实现类”。之后如果加载了新的实现类，假设不成立，JVM 会把编译好的代码作废，退回解释执行，这叫**反优化**（Deoptimization）。

编译好的机器码存放在**代码缓存**（Code Cache）里，它是一块堆外内存。代码缓存满了，JIT 就停止编译，程序会明显变慢，日志里会出现 `CodeCache is full. Compiler has been disabled` 的警告，可以用 `-XX:ReservedCodeCacheSize` 调大。

## 8.3 编译优化：方法内联与逃逸分析

**方法内联**：把被调用方法的代码，直接复制到调用的地方，省掉一次方法调用和一个栈帧。getter、setter 这种小方法几乎都会被内联，所以写成方法没有性能损失。内联更重要的作用是**扩大优化的视野**：编译器能看到的代码范围越大，能做的优化越多，下面的逃逸分析就依赖它。单元一的递归层数在 JIT 后变多，也是因为编译后的栈帧比解释执行时更小。

**逃逸分析**：分析一个对象的作用范围有没有“逃”出去。

- **不逃逸**：对象只在方法内部使用。
- **方法逃逸**：对象作为返回值或参数传到了别的方法。
- **线程逃逸**：对象被赋给了静态变量或其他线程能访问的字段。

对不逃逸的对象，JIT 可以做两项优化：

- **标量替换**：不创建对象，直接把它的字段拆成几个局部变量（“标量”）。对象根本不在堆上分配，也就不会产生垃圾。这是 HotSpot 实际做的优化；常说的“栈上分配”，HotSpot 并没有实现，效果靠标量替换达到。
- **锁消除**：不逃逸的对象不可能被别的线程访问，在它上面加的 synchronized 可以直接去掉（见 learn-juc 单元三）。

**用实验证明**：`examples/EscapeDemo.java` 在循环里调用 2 亿次 `distance()`，每次 new 一个 Point，Point 只在方法里用，没有逃逸。程序记录每轮的耗时和期间发生了几次 GC。JDK 17、`-Xmx64m` 实测：

```text
# 默认（逃逸分析开启）
第 1 轮：2 亿次 new Point，用时   66 ms，期间 GC   0 次
第 2 轮：2 亿次 new Point，用时  171 ms，期间 GC   0 次
第 3 轮：2 亿次 new Point，用时  169 ms，期间 GC   0 次

# -XX:-DoEscapeAnalysis（关闭逃逸分析）
第 1 轮：2 亿次 new Point，用时  277 ms，期间 GC 121 次
第 2 轮：2 亿次 new Point，用时  644 ms，期间 GC 121 次
第 3 轮：2 亿次 new Point，用时  643 ms，期间 GC 121 次
```

2 亿个 16 字节的 Point 就是 3.2GB，堆只有 64MB，真要分配的话一定会 GC 很多次，关掉逃逸分析后正是这样：每轮 121 次 GC。开着逃逸分析时一次 GC 都没有，说明这些 Point 根本没有在堆上分配，耗时也只有关掉时的四分之一左右。

所以“对象一定分配在堆上吗”的准确回答是：从 Java 语义上说都在堆上；但 HotSpot 的 C2 编译后，没有逃逸的对象会被标量替换掉，根本不分配。只在代码被 C2 编译后才生效，解释执行时照样在堆上分配。

## 面试这样说

**问：JVM 为什么既有解释器，又有 JIT 编译器？**

> 解释器不需要编译，程序启动就能跑，但逐条翻译字节码，执行慢；JIT 把热点代码编译成机器码，执行快，但编译要花时间和内存。大部分代码只跑几次，不值得编译，所以 JVM 先解释执行，用方法调用计数器和回边计数器发现热点，再交给 JIT。HotSpot 用分层编译：C1 编译快、优化简单，C2 编译慢但根据运行时收集的信息做激进优化，常见路线是解释、C1、C2。假设失效时还会反优化退回解释执行。

**问：对象一定分配在堆上吗？什么是逃逸分析？**

> 从语义上说对象都在堆上，但 JIT 会做逃逸分析，判断对象有没有逃出方法或线程。没有逃逸的对象可以标量替换，把字段拆成局部变量，不在堆上分配，也就没有 GC 压力；还可以做锁消除。HotSpot 并没有真正实现栈上分配，靠的是标量替换。我做过实验：循环 new 两亿个不逃逸的小对象，开着逃逸分析一次 GC 都没有，关掉后每轮一百多次 GC，耗时是原来的近四倍。
