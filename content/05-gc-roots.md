# 单元五 垃圾判定：哪些对象可以回收

本单元的核心：GC 不是去找垃圾，而是去找活对象：从 **GC Roots** 出发，顺着引用能走到的对象都活着，走不到的就是垃圾。

**学完这个单元，你能：**

- 说清引用计数为什么不行，可达性分析怎么判断对象的死活，并列出常见的 GC Roots。
- 说出强、软、弱、虚四种引用在 GC 时的区别和各自的用途。
- 解释找 GC Roots 时为什么必须停下所有业务线程，以及线程为什么只能在安全点停下。

单元四讲了对象怎么出生，本单元讲对象怎么“被判死刑”。顺序是：先用实验否定最直观的引用计数（5.1），再讲 JVM 实际用的可达性分析（5.2），然后看四种引用怎么影响判定（5.3），补上方法区里的回收（5.4），最后看“找根”这一步为什么要停顿（5.5）。

## 5.1 引用计数法为什么不行

最直观的办法是给每个对象记一个**引用计数**：有一个地方引用它就加 1，引用断开就减 1，减到 0 就是垃圾。实现简单，判定也及时。但它解决不了**循环引用**：a 引用 b、b 引用 a，即使外界谁都不再引用它们，两者的计数也永远是 1。

JVM 用的是不是引用计数，跑一下就知道。`examples/CycleRef.java` 让两个各带 10MB 数据的对象互相引用，再去掉外部引用，然后调用 `System.gc()`。用弱引用当“探针”（弱引用不影响回收，对象被回收后 `get()` 返回 null，5.3 节讲）。JDK 17 加 `-Xlog:gc` 实测：

```text
[0.003s][info][gc] Using G1
[0.018s][info][gc] GC(0) Pause Full (System.gc()) 28M->4M(40M) 1.368ms
a 被回收了吗：true
b 被回收了吗：true
```

堆从 28MB 降到 4MB，互相引用的两个对象连同 20MB 数据都被回收了。所以 HotSpot 判断对象死活用的不是引用计数。

## 5.2 可达性分析与 GC Roots

**可达性分析**：从一组叫 **GC Roots** 的起点出发，顺着对象之间的引用往下走，能走到的对象就是活的；走不到的，不管它们之间有没有互相引用，都是垃圾。

把它想成放风筝：GC Roots 是人手里攥着的线头，顺着线能牵到的风筝都还在天上；线断了的风筝，就算两只风筝绑在一起（循环引用），也一样会飞走。

**哪些对象可以作为 GC Roots？** 简单说，就是“此刻一定还在用的东西”直接引用的对象：

- 虚拟机栈中局部变量表引用的对象：正在执行的方法里的参数、局部变量。
- 本地方法栈中 JNI 引用的对象。
- 类的静态变量引用的对象。
- 常量引用的对象，比如字符串常量池里的引用。
- 被 synchronized 持有的对象（锁对象）。
- JVM 内部的引用：基本类型对应的 Class 对象、常驻的异常对象、系统类加载器等。

回到 CycleRef：`a = null; b = null;` 之后，两个对象只剩彼此之间的引用，没有任何一条路从 GC Roots 通向它们，所以被判定为垃圾。

## 5.3 四种引用

只有“可达”和“不可达”两种状态，有些场景不够用：比如缓存，希望内存充足时留着，紧张时可以丢掉。所以 Java 把引用分成四种强度：

| 引用 | 写法 | 什么时候被回收 | 典型用途 |
| --- | --- | --- | --- |
| 强引用 | `Object o = new Object()` | 只要强引用还在，宁可 OOM 也不回收 | 绝大多数引用 |
| 软引用 | `new SoftReference<>(obj)` | 内存不够时（OOM 之前）才回收 | 内存敏感的缓存 |
| 弱引用 | `new WeakReference<>(obj)` | 下一次 GC 就回收 | `WeakHashMap`、`ThreadLocalMap` 的 key |
| 虚引用 | `new PhantomReference<>(obj, queue)` | `get()` 永远返回 null；对象被回收后，引用本身被放进队列 | 得知对象已被回收，清理堆外资源 |

`examples/RefTypes.java` 各用一种引用指向一个 8MB 的数组，先 GC 一次，再不停分配内存直到内存吃紧。JDK 17、`-Xmx64m` 实测：

```text
GC 之前  强=true  软=true  弱=true  虚 get()=null
一次 GC  强=true  软=true  弱=false  虚引用进队列=true
内存吃紧（又分配了 36 MB）后  软=false
```

- 一次普通的 GC：弱引用指向的数组被回收，虚引用的数组也被回收、引用进了队列；软引用的数组还在，因为内存还够。
- 内存吃紧时：JVM 在抛 OOM 之前回收了软引用的数组。
- 虚引用的 `get()` 从一开始就是 null，它不是用来访问对象的，而是用来**收到“对象已经被回收”的通知**。2.5 节的直接内存就是这样释放的：`DirectByteBuffer` 对象被回收后，JDK 通过虚引用（`Cleaner`）得知，再去释放对应的堆外内存。

ThreadLocal 的 key 用弱引用、以及由此引出的内存泄漏，见 learn-juc 单元九。

## 5.4 对象的“缓刑”与方法区的回收

**finalize**：重写了 `finalize()` 的不可达对象，会先被放进队列，等专门的线程调用一次 `finalize()`，对象甚至能在里面把自己重新挂到某个引用上“复活”。这个机制执行时机不确定、拖慢回收，JDK 9 起已经废弃，释放资源请用 try-with-resources。

**方法区也会回收**，但条件苛刻，收益也小：

- **废弃常量**：比如字符串常量池里一个没有任何地方引用的字符串。
- **不再使用的类**，要同时满足三个条件：
  1. 这个类的所有实例都已经被回收；
  2. 加载这个类的类加载器已经被回收；
  3. 这个类的 `Class` 对象没有在任何地方被引用（比如反射）。

第二个条件决定了：由启动类、平台类、应用类加载器加载的类，基本不会被卸载，因为这些加载器一直活着。只有自定义类加载器加载的类才有机会卸载，这就是单元三说的“热部署要丢掉旧加载器”，也是元空间泄漏最常见的根源。

## 5.5 找根要停顿：STW 与安全点

可达性分析要从 GC Roots 出发，而 GC Roots 大量藏在各个线程的栈帧里。如果业务线程一边跑一边改引用，GC 刚找到的根下一刻可能就变了。所以至少在**枚举 GC Roots 的那一刻**，必须让所有业务线程停下来，这就是 **Stop The World（STW）**。

线程不能在任意一条指令上停下，只能停在**安全点**（safepoint）：

- 在安全点上，JVM 预先记好了“栈帧里哪些位置存的是引用”（这张表叫 OopMap），GC 直接查表，不用扫描整个栈去猜。
- 安全点设在方法调用、循环跳回、抛出异常这类位置。
- 需要 STW 时，JVM 设一个标志；线程跑到最近的安全点时检查这个标志，发现要停就自己挂起。
- 正在 sleep 或者等锁的线程不执行代码，没法“跑到”安全点。它们所在的代码段引用关系不会变化，叫**安全区域**：进入时声明一下，GC 就可以不等它；离开时检查 GC 是否完成，没完成就等着。

所以一次 STW 的时长 = **所有线程跑到安全点的时间** + **GC 真正干活的时间**。用 `-Xlog:safepoint` 能看到每次安全点的这两段时间（JDK 17 实测，节选）：

```text
[0.017s][info][safepoint] Safepoint "G1TryInitiateConcMark", Time since last: 8187209 ns, Reaching safepoint: 10500 ns, At safepoint: 278083 ns, Total: 288583 ns
```

`Reaching safepoint` 是等线程到齐用的 10.5 微秒，`At safepoint` 是停下来干活的 278 微秒。线上偶尔会遇到某个线程迟迟跑不到安全点，所有线程都陪它干等，日志里的 `Reaching safepoint` 就会异常地大。

## 面试这样说

**问：怎么判断一个对象可以被回收？哪些对象可以作为 GC Roots？**

> HotSpot 用可达性分析：从 GC Roots 出发顺着引用链往下走，走不到的对象就可以回收。不用引用计数，是因为它解决不了循环引用，两个互相引用的对象计数永远不为零。GC Roots 主要有：虚拟机栈里局部变量引用的对象、本地方法栈里 JNI 引用的对象、静态变量引用的对象、常量引用的对象、被 synchronized 持有的对象，以及 JVM 内部的引用比如系统类加载器。

**问：强、软、弱、虚四种引用有什么区别？**

> 强引用只要还在就不回收，宁可 OOM；软引用在内存不足、要抛 OOM 之前才回收，适合做缓存；弱引用下一次 GC 就回收，WeakHashMap 和 ThreadLocalMap 的 key 用的就是它；虚引用的 get 永远是 null，不影响对象的生命周期，作用是对象被回收后把引用放进队列通知我们，DirectByteBuffer 就靠它释放堆外内存。

**问：什么是安全点？为什么 GC 要等线程到达安全点？**

> 枚举 GC Roots 时引用关系不能变，所以要 STW。但线程不能随便停，只有在安全点上，JVM 才记录了栈帧里哪些位置是引用（OopMap），GC 才能准确找到根。安全点设在方法调用、循环回跳、异常跳转这些位置，线程跑到安全点时检查标志，主动挂起。sleep 或阻塞的线程处在安全区域，引用关系不会变，GC 不用等它们。
