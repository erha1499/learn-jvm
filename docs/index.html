JVM 交互学习手册
文字版 示例代码 learn-juc

JVM 的知识点看起来很散：内存区域、类加载、GC、收集器、调优……其实它们都是同一个程序在不同阶段遇到的事。按程序“从源码到运行、从出生到回收、从上线到出问题”的顺序学，比按题背更容易记住。

整条主线可以这样理解：

  1. 代码怎么跑：javac 把源码编译成字节码，JVM 为每次方法调用压一个栈帧，在栈帧里逐条执行字节码；跑得多的热点代码，再由 JIT 编译成机器码。
  2. 东西放哪：运行时数据区分成线程私有的栈、程序计数器，和线程共享的堆、方法区。类加载器把类读进方法区，new 出来的对象放进堆。
  3. 对象怎么死：GC 从 GC Roots 出发找活对象，剩下的就是垃圾；按对象寿命分代，用不同的算法回收。
  4. 怎么回收得更好：收集器的演进就是把停顿越切越短，从 Serial 到 ZGC。
  5. 出了问题怎么查：用 jstat、jcmd、jstack、GC 日志和堆转储建立证据链。

怎么用这份文档

这份手册写给会写 Java、对 JVM 只有零散印象（听说过堆、栈、GC）的人，目标是理解原理、能动手观察，并能应付面试。内容按面试的主线取舍：内存结构、垃圾回收（可达性分析、回收算法、Minor GC 与 Full GC、CMS 与 G1）、类加载与双亲委派、内存问题排查讲透；字节码、JIT 只讲理解主线所需的部分。操作系统和并发只在用到的地方一两句话交代；锁和对象头的关系见姊妹篇 learn-juc 单元三。

每个单元都按同一个节奏组织：

  1. 先看现象，再学原理：单元开头列出学完能做到的几件事。能用代码复现的问题（i = i++ 还是 0、类没有按预期初始化、对象明明不用了却回收不掉），先给出可运行的代码和真实结果，再解释为什么。标着「深入一层（可跳过）」的部分是源码和底层细节，第一遍可以跳过。
  2. 动手：正文关键处嵌了可以一步一步执行的演示；文中的示例代码都在仓库的 examples/ 目录里，建议亲手跑一遍，再用 javap、jstat、jcmd 看一看。

单元一

字节码与执行

一个方法是怎么跑起来的

JVM 是一台“栈式机器”。每调用一个方法，就在线程的栈上压一个栈帧，字节码指令在栈帧的“局部变量表”和“操作数栈”之间搬数据、做计算；跑得多的热点代码，再由 JIT 编译成机器码。

学完这个单元，你能
  • 用 javap 读懂一段简单的字节码，并用栈帧解释 i = i++ 为什么还是 0。
  • 说清栈帧里有什么，以及 StackOverflowError 和哪些因素有关。
  • 说清 JVM 为什么既有解释器、又有 JIT 编译器。

JVM 的知识点很多，最好的起点是最小的那件事：一个方法到底是怎么执行的。顺序是：先看 JVM 的全貌（1.1），再用 javap 看一眼字节码（1.2），然后把字节码放进栈帧里一条条执行（1.3），接着看栈长到多高会溢出（1.4），补上另外两块线程私有的区域（1.5），最后看热点代码怎么变快（1.6）。

1.1 JVM 全景：从 .java 到运行

javac 不直接生成机器码，而是生成字节码（.class 文件），它是 JVM 的“指令集”。每个平台各有一个 JVM 负责执行字节码，所以 Java 能“一次编写，到处运行”。我们用的 JVM 是 OpenJDK 和 Oracle JDK 里的 HotSpot。（JDK = JRE + 编译器和诊断工具，JRE = JVM + 核心类库。）

一个 Java 程序跑起来，会依次经过 JVM 的三大部分：

从左往右读：类加载子系统把 .class 读进来，类的信息放进方法区（单元三）；运行时数据区里，堆和方法区所有线程共享，每个线程另有自己的虚拟机栈、本地方法栈和程序计数器（单元二）；执行引擎里，解释器逐条执行字节码，热点代码交给 JIT 编译器（1.6 节），垃圾收集器负责回收堆里没用的对象（单元五到七）。

1.2 字节码：用 javap 看一眼

拿一个最简单的方法开刀（examples/Calc.java）：

static int add(int a, int b) {
    int c = a + b;
    return c * 2;
}

编译后用 javap -c Calc 反汇编，JDK 17 输出：

static int add(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: istore_2
     4: iload_2
     5: iconst_2
     6: imul
     7: ireturn
  • 左边的数字是指令在方法字节码里的偏移量，1.5 节的程序计数器记的就是它。
  • 指令名的第一个字母是数据类型：i 是 int，l 是 long，a 是引用。
  • iload_0 把 0 号局部变量压到操作数栈顶；istore_2 把栈顶弹出，存进 2 号局部变量；iadd、imul 从栈顶弹出两个数，算完再压回去。

用 javap -v 还能看到这个方法的 stack=2, locals=3：操作数栈最深 2 层，局部变量表要 3 个槽位（a、b、c）。这两个数在编译时就算好了，所以调用方法时 JVM 能直接分配一个大小正好的栈帧。

javap -v 还会打印 class 文件里的常量池：类名、方法名、字符串字面量这些“符号”集中存在这里，指令里只写编号。比如 main 调用 add 的指令是 invokestatic #13，意思是“调用常量池 13 号登记的方法”，13 号写的是 Calc.add:(II)I。等到运行时，JVM 才把这个符号换成方法的真实地址（单元三的“解析”）。

1.3 栈帧：局部变量表 + 操作数栈

每个线程都有一个虚拟机栈。线程每调用一个方法，就在栈顶压入一个栈帧；方法返回时，栈帧弹出。栈帧里有四样东西：

部分存什么
局部变量表方法参数和局部变量，按槽位编号；实例方法的 0 号是 this，long 和 double 各占两个槽位
操作数栈计算用的临时数据，指令从这里取数、往这里放结果
动态链接指向所属类的运行时常量池（常量池加载进内存后的样子），用来把 #13 这样的符号换成真实地址
返回地址方法返回后，调用方从哪条指令继续

学字节码只需要盯住前两样。把栈帧想成一个工位：

  • 局部变量表是工位上一排编了号的抽屉，每个变量占一个抽屉。
  • 操作数栈是工位中间的一个托盘，东西只能从最上面放、从最上面拿。
  • 字节码就是操作说明：iload_1 = 从 1 号抽屉拿出一个数放到托盘最上面；iadd = 拿走托盘最上面两个数，相加后把结果放回；istore_2 = 把托盘最上面的数收进 2 号抽屉。

按这个思路把 add(3, 4) 走一遍。调用时压入一个新栈帧，参数 3、4 已经放在 0 号和 1 号抽屉里：

走完这几步，抓住三点：

  • 托盘上最多同时放两个数（偏移 1），抽屉一共三个，正是 javap 里的 stack=2, locals=3。
  • load 只是把抽屉里的值复制一份放上托盘，a、b 一直留在抽屉里。
  • iadd、imul 只和托盘打交道，不碰抽屉；结果要靠 store 才能收回抽屉。

一个反直觉的现象：examples/IPlusPlus.java

int i = 0;
i = i++;
System.out.println("i = i++ 之后，i = " + i);

int j = 0;
j = ++j;
System.out.println("j = ++j 之后，j = " + j);

JDK 17 实测输出：

i = i++ 之后，i = 0
j = ++j 之后，j = 1

看字节码就清楚了（javap -c IPlusPlus，节选）：

// i = i++              // j = ++j
0: iconst_0             19: iconst_0
1: istore_1             20: istore_2
2: iload_1              21: iinc   2, 1
3: iinc   1, 1          24: iload_2
6: istore_1             25: istore_2

关键在 iinc：它直接改抽屉里的值，不经过托盘。

  • i = i++：先 iload_1 把旧值 0 放上托盘，再 iinc 把抽屉里的 i 改成 1，最后 istore_1 把托盘上的 0 收回抽屉，覆盖了刚加好的 1。
  • j = ++j：先 iinc 把抽屉里的 j 改成 1，再 iload_2 把 1 放上托盘，存回去的也是 1。

“后置 ++ 先取值再自增”，在字节码里就是“先 load 再 iinc”。

1.4 方法调用与 StackOverflowError

方法 A 调用方法 B，就在 A 的栈帧上面再压一个 B 的栈帧；B 返回，B 的栈帧弹出。递归就是同一个方法的栈帧一层层往上叠，每一层都有自己的一套抽屉，互不干扰。

线程的栈大小是固定的（-Xss 设置），栈帧叠到装不下，就抛 StackOverflowError。examples/StackDepth.java 用两个递归方法测能叠多少层：一个没有局部变量，一个有 8 个 long 局部变量。加 -Xint（只用解释器）让结果稳定，JDK 17 实测：

栈大小没有局部变量8 个 long 局部变量
-Xss1m9671 层4145 层
默认（这台 macOS 上是 2MB，Linux x64 上是 1MB）20594 层8826 层
-Xss4m42439 层18188 层
  • 栈越大，能叠的层数越多，大致成正比。
  • 栈帧越大，层数越少：8 个 long 占 16 个槽位，每层栈帧变大，同样的栈只能放下一半不到。
  • 不加 -Xint 时，层数会多出一倍以上，而且每次都不一样，所以“递归多少层会溢出”没有固定答案（原因见 1.6 节）。

栈也不是越大越好：每个线程都要占一份栈空间，-Xss 太大，能创建的线程就少了；线程太多、内存不够分配新线程的栈时，抛出的是 OutOfMemoryError: unable to create native thread。线上遇到 StackOverflowError，先看异常栈里反复出现的那个方法，多半是递归没有正确的结束条件，而不是栈不够大。

1.5 程序计数器与本地方法栈

除了虚拟机栈，每个线程还有两块私有的小区域：

  • 程序计数器：记录当前线程执行到哪条字节码，存的就是 1.2 节那一列偏移量。CPU 会在多个线程之间来回切换，切回来时要知道从哪里接着跑，所以每个线程一个。执行 native 方法时它的值是空的（undefined）。它是唯一一块规范里不会发生 OutOfMemoryError 的区域。
  • 本地方法栈：给 native 方法（用 C/C++ 实现的方法，比如 Thread.sleep()）用的栈。HotSpot 把它和虚拟机栈合成了一个。

这三块线程私有的区域随线程创建而创建、随线程结束而销毁，方法一返回栈帧就弹出，不需要垃圾回收。

1.6 解释器与 JIT：热点代码才编译

  • 解释器：读一条字节码，执行一条。程序马上就能跑，但每次都要重新“翻译”，慢。
  • JIT（即时编译器）：把一整个方法编译成本地机器码，之后直接执行，快。但编译本身要花时间和内存。

好比同声传译和书面翻译：解释器说一句翻一句，马上能开讲；JIT 是把反复要讲的稿子提前翻好，翻的时候费工夫，之后照着念就快了。只有反复讲的稿子才值得翻。

examples/JitWarmup.java 把同一个方法分 8 批执行，每批调用 200 次，记录每批耗时。JDK 17 实测：

批次默认（解释器 + JIT）-Xint（只用解释器）
第 1 批879 µs1355 µs
第 2 批555 µs1444 µs
第 3 批262 µs1385 µs
第 4 到 8 批约 195 µs约 1380 µs

默认模式下一批比一批快，第 4 批起稳定下来，方法被 JIT 编译好了，比纯解释执行快 7 倍。

怎么判断热点：JVM 给每个方法记两个数：方法被调用的次数，和循环跳回开头的次数（一个只调用一次、但循环了几百万圈的方法也是热点）。超过阈值就在后台线程里编译，编译完成前继续解释执行，不会卡住业务。

分层编译：HotSpot 有两个 JIT 编译器。C1 编译快、优化简单；C2 编译慢，但会根据运行时收集到的信息（常走哪个分支、实际是什么类型）做激进优化，生成的代码最快。常见路线是：解释执行 → C1 先编一个能跑的版本、顺便收集信息 → 足够热了再交给 C2。

为什么不一开始就全部编译？ 大部分代码只执行一两次，编译它们得不偿失，还会拖慢启动；而且 JIT 能利用运行时信息，做出比提前编译更激进的优化。

1.4 节的递归层数也是因为 JIT：编译后的栈帧比解释执行时小，同样的栈能叠更多层；而方法在递归到第几层时被编译好，每次运行都不一样。JIT 还有一项和对象分配有关的重要优化，叫逃逸分析，在 4.5 节讲。

深入一层从 PrintCompilation 看分层编译

加 -XX:+PrintCompilation 运行 JitWarmup，能看到 work 方法的每一次编译（JDK 17 实测）：

     15    7 %     3       JitWarmup::work @ 4 (29 bytes)
     15    8       3       JitWarmup::work (29 bytes)
     15    9 %     4       JitWarmup::work @ 4 (29 bytes)
     16    7 %     3       JitWarmup::work @ 4 (29 bytes)   made not entrant
     28  106       4       JitWarmup::work (29 bytes)
     29    8       3       JitWarmup::work (29 bytes)   made not entrant

各列依次是：启动后的毫秒数、编译编号、标记、层级（3 是 C1，4 是 C2）、方法名。% 表示 OSR（栈上替换）：一个正在运行的长循环，等不到方法下次被调用，就在循环中途切换到编译好的版本，@ 4 是切入点的字节码偏移量，正是循环开头。made not entrant 表示旧版本被新版本取代、不再使用。C2 的优化建立在假设上（比如“这个接口只有一个实现类”），假设被打破时，JVM 会作废编译好的代码、退回解释执行，这叫反优化。

面试这样说

栈帧里有什么？i = i++ 为什么还是原来的值？
每次方法调用，JVM 在线程的虚拟机栈上压一个栈帧，里面有局部变量表、操作数栈、动态链接和返回地址，局部变量表和操作数栈的大小在编译时就确定了。字节码是基于栈的指令，load 把局部变量压到操作数栈，store 把栈顶弹回局部变量。i = i++ 编译成 iload、iinc、istore 三条：iload 先把旧值压栈，iinc 直接在局部变量表里把 i 加一，最后 istore 又把栈上的旧值写回 i，加一的结果被覆盖了。
什么情况下会 StackOverflowError？怎么排查？
线程栈的大小由 -Xss 固定，方法每调用一层就压一个栈帧，递归太深、栈帧叠满了就抛 StackOverflowError。能叠多少层取决于栈大小和栈帧大小，局部变量越多栈帧越大。排查时看异常栈里重复出现的方法，一般是递归缺少正确的结束条件，应该改代码，而不是盲目调大 -Xss，那样会减少能创建的线程数。
JVM 为什么既有解释器，又有 JIT 编译器？
解释器不需要编译，程序启动就能跑，但逐条翻译字节码，执行慢；JIT 把热点代码编译成机器码，执行快，但编译要花时间和内存。大部分代码只跑几次，不值得编译，所以 JVM 先解释执行，用方法调用次数和循环回边次数找出热点，再交给 JIT。HotSpot 用分层编译：C1 编译快、优化简单，C2 编译慢但会根据运行时信息做激进优化，常见路线是解释、C1、C2。

自测

  1. i = i++ 执行完 i 为什么还是 0？用局部变量表和操作数栈解释。
    字节码是 iload_1、iinc 1,1、istore_1：先把 i 的旧值 0 压到操作数栈；iinc 直接把局部变量表里的 i 改成 1，不经过操作数栈；最后 istore_1 把栈上的旧值 0 写回 i，覆盖了 1。j = ++j 是先 iinc 再 iload，所以存回的是 1。
  2. 栈帧里有哪几部分？局部变量表和操作数栈的大小是什么时候确定的？
    局部变量表、操作数栈、动态链接、返回地址。局部变量表的槽位数（locals）和操作数栈的最大深度（stack）在编译时就算好了，写在 class 文件方法的 Code 属性里，所以调用方法时 JVM 能直接分配一个大小正好的栈帧。
  3. 同样的 -Xss，为什么方法的局部变量越多，能递归的层数越少？
    每层递归都要压一个栈帧，局部变量越多，局部变量表越大，栈帧就越大；栈的总大小固定，能放下的栈帧就越少。实测默认栈下，没有局部变量能递归 20594 层，8 个 long 局部变量只有 8826 层（都用 -Xint）。
  4. 程序计数器为什么要线程私有？它会发生 OOM 吗？
    CPU 在多个线程之间切换，切回来时每个线程都要知道自己执行到了哪条字节码，所以每个线程要有自己的计数器，互不干扰。它只存一个位置，大小固定，是 JVM 规范里唯一不会发生 OutOfMemoryError 的区域。
  5. 一个 .java 文件从编译到执行，经过了 JVM 的哪几部分？
    javac 先把源码编译成 .class 字节码（这一步在 JVM 之外）。运行时，类加载子系统把类读进来，类的信息放进方法区；执行引擎为每次方法调用在线程的虚拟机栈上压栈帧，解释器逐条执行字节码，热点代码由 JIT 编译成机器码；new 出来的对象放在堆里，由垃圾收集器回收。
  6. 解释器和 JIT 编译器各自的优势是什么？为什么不一开始就全部编译？
    解释器不用编译，程序马上就能跑；JIT 编译后执行快（实测稳定后快 7 倍）。不全部提前编译，一是大部分代码只执行几次，编译它们得不偿失、拖慢启动；二是 JIT 能利用运行时收集的信息（常走哪个分支、实际类型）做更激进的优化。
  7. JVM 怎么判断一段代码是“热点”？C1 和 C2 有什么区别？
    JVM 给每个方法记两个数：方法被调用的次数，和循环跳回开头的次数（回边），超过阈值就提交给后台线程编译，编译完成前继续解释执行。C1 编译快、只做简单优化，还会收集运行信息；C2 编译慢，根据收集到的信息做激进优化，代码最快。常见路线是解释执行 → C1 → C2。
单元二

运行时数据区

堆、方法区与直接内存

线程私有的区域（栈、程序计数器）随线程生灭，用不着 GC；线程共享的堆和方法区才是垃圾回收和 OutOfMemoryError 的主战场。

学完这个单元，你能
  • 说出运行时数据区的每一块存什么、是否线程共享、满了会抛什么错。
  • 说清字符串常量池在哪、intern() 做了什么，判断几个 == 的结果。
  • 看到一条 OutOfMemoryError，判断是哪块内存满了、该往哪个方向查。

单元一讲了线程私有的三块区域。本单元把视角拉到整个 JVM 进程：先看全貌（2.1），再分别看堆（2.2）、方法区（2.3）、方法区里最常被问到的字符串常量池（2.4），以及不归 JVM 规范管、却同样会溢出的直接内存（2.5），最后把各种 OOM 放在一起对照（2.6）。

2.1 全景：五块区域 + 一块堆外内存

把 JVM 进程想成一座工厂：方法区是档案室，存着每种产品的图纸（类的信息）；堆是仓库，所有造出来的产品（对象）都堆在这里；每个工人（线程）有自己的一叠工位（虚拟机栈：每调用一个方法叠上一个工位，就是单元一的栈帧）和一个进度条（程序计数器）。档案室和仓库大家共用，工位各用各的。

区域存什么线程满了会抛
程序计数器当前执行到哪条字节码私有不会
虚拟机栈栈帧：局部变量表、操作数栈……私有StackOverflowError
本地方法栈native 方法的栈帧私有StackOverflowError
堆对象实例和数组共享OutOfMemoryError: Java heap space
方法区类的元数据、运行时常量池共享OutOfMemoryError: Metaspace（JDK 8 起）
直接内存（不属于运行时数据区）NIO 的堆外缓冲区共享OutOfMemoryError: ... direct buffer memory

一段代码里的各种东西分别落在哪里，是最容易混的地方：局部变量在栈帧里；new 出来的对象在堆里；类的结构和方法字节码在方法区；而静态变量在 JDK 7 之后跟着类的 Class 对象放在堆里，不在方法区（每个类加载后，堆里都有一个代表它的 Class 对象，单元三讲）。

栈里存的是对象还是指针？ 局部变量如果是基本类型（int、long……），栈帧里存的就是值本身；如果是对象，栈帧里只存一个引用（可以理解成对象的地址），对象本身在堆里。对象的字段，不管是不是基本类型，都跟着对象在堆里。

2.2 堆：对象住在这里

  • 几乎所有对象和数组都在堆上分配（例外见 4.5 节的逃逸分析）。堆被所有线程共享，是垃圾收集器管理的主要区域，所以也叫“GC 堆”。
  • 为了回收效率，堆通常分成新生代（又分成 Eden 和两个 Survivor）和老年代。为什么这样分、对象怎么在里面搬家，单元六细讲。
  • 大小用 -Xms（初始）和 -Xmx（最大）设置。不设置时，最大堆默认是物理内存的 1/4，初始堆是 1/64：这台 24GB 内存的机器上，java -XX:+PrintFlagsFinal -version 显示 MaxHeapSize 是 6GB，InitialHeapSize 是 384MB。服务端程序常把两者设成一样，省去运行时扩容、缩容的开销。

2.3 方法区：类的“档案室”

方法区存放已加载的类的元数据：类名、父类、接口、字段和方法的描述、方法的字节码，以及运行时常量池（1.2 节 javap -v 看到的常量池，类加载后搬进内存，就成了运行时常量池）。

方法区是 JVM 规范里的逻辑概念，HotSpot 在不同版本里用不同的方式实现它：

JDK 版本实现位置大小限制
7 及以前永久代（PermGen）JVM 管理的一块固定区域-XX:MaxPermSize，默认很小
8 及以后元空间（Metaspace）本地内存（操作系统的内存）-XX:MaxMetaspaceSize，默认不限

为什么用元空间取代永久代？

  • 永久代的大小很难设：一个应用会加载多少类，事先说不准。大量使用动态代理、CGLIB、JSP 的应用，常常撞上 OutOfMemoryError: PermGen space。
  • 元空间放在本地内存里，默认不设上限，只受物理内存限制。
  • 另一个原因是 HotSpot 要合并 JRockit 虚拟机的代码，JRockit 没有永久代。

两个参数经常被混淆：-XX:MaxMetaspaceSize 是元空间的上限；-XX:MetaspaceSize 不是初始大小，而是一个阈值：元空间用量第一次达到它时，JVM 触发一次 GC 来卸载不再使用的类（日志里的原因是 Metadata GC Threshold；Serial、Parallel 收集器做的是 Full GC，即回收整个堆和方法区的 GC，6.5 节），之后再动态调整这个阈值。

元空间还会溢出吗？ 会。examples/MetaspaceOOM.java 让每个新的类加载器把同一份字节码再定义一次（同名的类，换一个加载器就是一个新的类，单元三细讲），并且一直引用着这些类。限制元空间为 16MB，JDK 17 实测：

定义了 2671 个类后：java.lang.OutOfMemoryError: Metaspace

真实项目里，元空间溢出通常是动态生成的类太多，而且生成它们的类加载器一直没被回收，类就卸载不掉。

2.4 字符串常量池与 intern

字符串常量池（StringTable）是 JVM 里一张全局的哈希表，记录着“这个内容的字符串，对应堆里的哪个 String 对象”。代码里的字符串字面量（"hello"）在第一次执行到时进池；调用 s.intern() 也会：池里已经有相同内容的，就返回池里那个对象；没有，就把 s 的引用登记进池，再返回 s。

JDK 7 把字符串常量池从永久代挪到了堆里。好处是池里的字符串没人用了也能被正常回收，永久代也不再被大量字符串撑爆。这个变化还改变了 intern() 的行为：池里只需要记一个引用，不用再把字符串复制一份。

examples/StringPool.java 把常见的几种情况都跑了一遍，JDK 17 实测输出（节选）：

1. "hello" == "hello"            : true
2. new String("hello") == "hello": false
3. c.intern() == "hello"         : true
4. s1.intern() == s1             : true
5. "javm" == s1                  : true
6. s3.intern() == s3             : false

逐行看：

  • 1：两个字面量都从池里取，是同一个对象。
  • 2、3：new String("hello") 一定在堆里新建一个对象，和池里的不是同一个；intern() 返回池里那个。
  • 4、5：s1 = new String("ja") + new String("vm") 是运行时拼出来的，内容 "javm" 在池里还没有。s1.intern() 把 s1 本身登记进池，所以返回的就是 s1。之后第一次执行到字面量 "javm"，去池里一查，拿到的也是 s1。
  • 6："hello" 早在第 1 行就进池了，s3.intern() 返回的是池里那个老对象，不是 s3。

String s = new String("abc") 创建了几个对象，分别在哪？ 局部变量 s 在栈帧里，存的是引用；字面量 "abc" 如果池里还没有，就在堆里创建一个 String 并登记进字符串常量池；new 再在堆里创建一个新的 String 对象，s 指向的是它。所以是两个对象（池里已有 "abc" 时是一个），s == "abc" 为 false。

2.5 直接内存

直接内存不属于运行时数据区，是 NIO 通过 ByteBuffer.allocateDirect() 直接向操作系统申请的堆外内存，Java 对象里只留一个 DirectByteBuffer 作为“遥控器”。

为什么 NIO 要用它？ 读写文件或网络时，操作系统需要一块地址固定的内存。堆里的对象会被 GC 挪来挪去，所以用堆内的 byte 数组做 IO，JVM 得先把数据复制到一块堆外内存，再交给操作系统。直接用堆外内存，就省掉了这次复制。Netty 这类网络框架大量使用直接内存。

  • 大小受 -XX:MaxDirectMemorySize 限制，不设置时默认和最大堆差不多大。
  • 堆外内存要等 DirectByteBuffer 对象被 GC 回收时才释放（5.3 节的虚引用）。如果堆很大、很少 GC，堆外内存可能迟迟不释放。

examples/DirectOOM.java 每次申请 1MB 直接内存并一直持有，限制为 10MB，JDK 17 实测：

申请了 10 MB 直接内存后：java.lang.OutOfMemoryError: Cannot reserve 1048576 bytes of direct buffer memory (allocated: 10485760, limit: 10485760)

2.6 OutOfMemoryError 速查

先分清两个概念：内存泄漏是不再使用的对象还被引用着，GC 回收不掉；内存溢出是申请内存时没有足够的空间。泄漏积累多了会导致溢出；但溢出不一定是泄漏，也可能是数据量真的大、堆真的不够。

堆溢出最常见。examples/HeapOOM.java 不停地往 List 里加 100KB 的数组，堆限制为 20MB，并让 JVM 在溢出时自动转储堆，JDK 17 实测：

面试这样说

堆和栈有什么区别？
用途不同：栈保存方法调用的栈帧，里面是局部变量和操作数栈，基本类型存值、对象只存引用；堆保存对象实例和数组。生命周期不同：栈帧随方法调用压入、随返回弹出，不需要 GC；堆里的对象由 GC 判断何时回收。共享性不同：每个线程有自己的栈，堆被所有线程共享，所以并发问题出在堆上的共享对象。出错也不同：栈太深抛 StackOverflowError，堆放不下抛 OutOfMemoryError: Java heap space。
JVM 内存区域是怎么划分的？
分成线程私有和线程共享两类。私有的是程序计数器、虚拟机栈和本地方法栈：程序计数器记录执行到哪条字节码；虚拟机栈每调用一个方法压一个栈帧，放局部变量和操作数栈；本地方法栈给 native 方法用。它们随线程生灭，不需要 GC。共享的是堆和方法区：堆放对象实例，是 GC 的主要区域，分新生代和老年代；方法区放类的元数据和运行时常量池，JDK 8 起用本地内存里的元空间实现。另外还有不属于运行时数据区的直接内存，给 NIO 用。
为什么用元空间取代永久代？
永久代大小固定，应用会加载多少类事先很难估，动态代理用得多就容易 PermGen 溢出；元空间放在本地内存，默认只受物理内存限制，更灵活。另一个原因是 HotSpot 合并 JRockit 时，JRockit 没有永久代。顺带一提，JDK 7 已经先把字符串常量池和静态变量挪到了堆里。
字符串常量池在哪？String s = new String("abc") 创建了几个对象？
JDK 7 起字符串常量池在堆里，它是一张全局的哈希表，记录“这个内容的字符串对应堆里哪个 String 对象”。字面量第一次执行到时进池；调用 intern 时，池里有就返回池里的对象，没有就把当前对象的引用登记进去。new String("abc") 在池里还没有 "abc" 时创建两个对象：字面量在堆里创建一个并登记进池，new 再新建一个，s 指向新建的那个，所以 s == "abc" 是 false；池里已经有 "abc" 时只新建一个。变量 s 本身在栈帧里，存的是引用。
JVM 内存结构和 Java 内存模型有什么区别？
两者说的不是一回事。内存结构讲的是数据存放在哪：堆、栈、方法区这些区域。Java 内存模型（JMM）是并发里的概念，讲的是一个线程写的共享变量，什么时候对另一个线程可见，用 happens-before 规则描述，volatile、synchronized 靠它保证可见性和有序性。

自测

  1. 哪些内存区域是线程私有的？为什么它们不需要 GC？
    程序计数器、虚拟机栈、本地方法栈。它们随线程创建而创建、随线程结束而销毁；栈帧在方法返回时自动弹出，里面的数据随之失效，内存什么时候能回收是确定的，不需要 GC 去判断。
  2. 方法里写 Shop s = new Shop()，s 和 Shop 对象分别在哪里？Shop 的静态变量呢？
    s 是局部变量，在当前方法栈帧的局部变量表里，存的是一个引用；Shop 对象在堆里。Shop 的静态变量在 JDK 7 之后跟着 Shop 的 Class 对象放在堆里；Shop 类本身的结构和方法字节码在方法区（元空间）。
  3. 方法区、永久代、元空间是什么关系？元空间还会 OOM 吗？
    方法区是 JVM 规范里的逻辑区域；永久代是 HotSpot 在 JDK 7 及以前对它的实现，元空间是 JDK 8 起的实现，放在本地内存。元空间默认不限大小，但仍会 OOM：设置了 MaxMetaspaceSize，或者动态生成大量类且类加载器不释放、物理内存耗尽时，都会抛 OutOfMemoryError: Metaspace。实测限制 16MB 时定义了 2671 个类后溢出。
  4. String s = new String("abc") 会创建几个对象？
    字符串常量池里还没有 "abc" 时是两个：字面量 "abc" 在堆里创建一个并登记进池，new 再在堆里新建一个；池里已经有 "abc" 时只新建一个。局部变量 s 在栈帧里，指向 new 出来的那个，所以 s == "abc" 是 false。
  5. s1 = new String("ja") + new String("vm")，调用 s1.intern() 后，"javm" == s1 为什么是 true？
    s1 是运行时拼出来的，内容 "javm" 在常量池里还没有。JDK 7 起常量池在堆里，intern() 发现池里没有，就把 s1 这个对象的引用登记进池并返回 s1。之后代码里第一次执行字面量 "javm"，去池里查到的就是 s1，所以相等。如果 "javm" 字面量在 intern 之前已经进池，结果就是 false（StringPool 的第 6 行就是这种情况）。
  6. 直接内存是什么？NIO 为什么要用它？
    直接内存是 NIO 通过 ByteBuffer.allocateDirect() 向操作系统申请的堆外内存，不属于运行时数据区，受 -XX:MaxDirectMemorySize 限制。操作系统做 IO 需要地址固定的内存，而堆里的对象会被 GC 移动，用堆内数组做 IO 要先复制到堆外；直接内存省掉了这次复制。它在 DirectByteBuffer 对象被回收时才释放。
  7. 看到 OutOfMemoryError: Metaspace，你会往哪个方向查？
    元空间满了，说明类太多或者类卸载不掉。查加载了多少类、由哪些类加载器加载（如 jcmd <pid> VM.classloader_stats、jstat -class），重点看动态代理、CGLIB、脚本引擎、热部署这些会动态生成类的地方，以及是否有自定义类加载器一直被引用着、无法回收。
  8. 内存泄漏和内存溢出有什么区别？
    内存泄漏是不再使用的对象仍被引用着，GC 回收不掉；内存溢出是申请内存时没有足够空间。泄漏积累多了会导致溢出，但溢出不一定是泄漏，也可能是数据量确实大、内存确实不够。
单元三

类加载

时机、过程与双亲委派

类加载把 .class 里的字节变成方法区里的类型信息和堆里的 Class 对象；它是“懒”的，第一次真正用到才初始化，而“由哪个类加载器加载”也是类身份的一部分。

学完这个单元，你能
  • 说出类加载的五个阶段，分清“准备”阶段的清零和“初始化”阶段的赋值。
  • 判断一段代码会不会触发某个类的初始化。
  • 讲清双亲委派的流程和好处，知道哪些场景要打破它。

单元二说类的信息放在方法区，本单元回答：类是什么时候、被谁、怎么放进去的。顺序是：先看一个静态代码块“该执行却没执行”的现象（3.1），再拆开类加载的各个阶段（3.2），总结哪些操作会触发初始化（3.3）和初始化的线程安全（3.4），然后认识类加载器（3.5）和双亲委派（3.6），最后看什么时候要打破它（3.7）。

3.1 先看现象：静态代码块什么时候执行

类的静态代码块在类初始化时执行，打印出来了就说明这个类初始化了。examples/InitTiming.java 里，Child 继承 Parent，money 是 Parent 的静态字段；Const 里有两个 static final 字段，一个是字面量，一个要运行时计算。JDK 17 实测输出：

1. 通过子类读父类的静态字段 Child.money
    [Parent 初始化]
2. 创建数组 new Child[3]
3. 读编译期常量 Const.NAME = jvm
4. 读非编译期常量 Const.NOW
    [Const 初始化]
5. new Child()
    [Child 初始化]
6. 同一个类不会初始化第二次：再 new Child()

几个“没执行”的地方都值得注意：

  • 第 1 步：money 是 Parent 声明的，通过 Child 去读，只初始化 Parent，Child 不初始化。
  • 第 2 步：创建 Child 类型的数组，Child 不初始化。数组是 JVM 另外生成的一个类型。
  • 第 3 步：NAME 是编译期常量，javac 编译时就把 "jvm" 直接抄进了 InitTiming 自己的常量池，运行时根本没碰 Const。
  • 第 4 步：NOW 虽然也是 static final，但它的值要运行 System.nanoTime() 才知道，读它就要先初始化 Const。
  • 第 6 步：一个类只初始化一次。

3.2 类的生命周期

一个类从被加载到被卸载，要经过这些阶段，其中验证、准备、解析合称链接：

阶段做什么
加载按类的全限定名找到字节（文件、jar 包、网络、运行时生成都可以），在方法区建立类的结构，在堆里生成一个 java.lang.Class 对象作为访问入口
验证检查字节码是否合法、安全：魔数、版本号、类型是否匹配、跳转有没有越界
准备给静态变量分配内存，并设成零值（0、false、null）；编译期常量在这一步直接设成最终值
解析把常量池里的符号引用（类名、方法名）换成直接引用（内存地址），可以推迟到第一次用到时再做
初始化执行类构造器 <clinit>()：按源码顺序执行所有静态变量的赋值语句和静态代码块；父类的 <clinit>() 先执行
使用、卸载卸载的条件很苛刻，见 5.4 节

最容易混的是准备和初始化：准备阶段只清零，初始化阶段才执行你写的赋值。<clinit>() 是编译器把所有静态赋值语句和静态代码块，按源码中出现的顺序拼成的一个方法。

一道经典题：examples/PreparePuzzle.java

static class Counter {
    static Counter INSTANCE = new Counter();  // ①
    static int a;                              // ②
    static int b = 0;                          // ③

    Counter() {
        a++;
        b++;
    }
}
// main 里打印 Counter.a 和 Counter.b

JDK 17 实测输出：

a = 1, b = 0
  • 准备阶段：INSTANCE = null，a = 0，b = 0。
  • 初始化阶段，按源码顺序执行 <clinit>()：
    • ① new Counter() 执行构造方法，a 变成 1，b 变成 1。
    • ② static int a; 没有赋值语句，<clinit>() 里没有它，a 保持 1。
    • ③ b = 0 把 b 重新赋成 0。

把 ① 挪到最后一行，结果就变成 a = 1, b = 1。

3.3 什么时候触发初始化

JVM 规范规定，只有下面几种“主动使用”才会触发类的初始化：

  1. 执行 new、读写静态字段（编译期常量除外）、调用静态方法。对应字节码的 new、getstatic、putstatic、invokestatic。
  2. 用反射调用，比如 Class.forName("...")。
  3. 初始化一个类时，如果父类还没初始化，先初始化父类。
  4. 虚拟机启动时，先初始化 main 方法所在的类。

除此以外的引用都不会触发初始化，比如 3.1 节的通过子类读父类静态字段、创建数组、读编译期常量。

还有一个常见的对比：ClassLoader.loadClass() 只加载，不初始化；Class.forName() 默认会初始化。examples/LoadVsInit.java 实测：

1. app.loadClass("LoadVsInit$Hello")
2. Class.forName("LoadVsInit$Hello")
    [Hello 初始化]

这也是早年 JDBC 要写 Class.forName("com.mysql.jdbc.Driver") 的原因：驱动类在静态代码块里把自己注册到 DriverManager，必须触发初始化才行。

3.4 类初始化是线程安全的

JVM 保证一个类的 <clinit>() 只执行一次。多个线程同时触发初始化，只有一个线程去执行，其他线程等它执行完。

examples/ClinitOnce.java 让 T1 先触发初始化，静态代码块里睡 1 秒；100ms 后 T2 也来用这个类。JDK 17 实测：

  T1 开始执行静态代码块，睡 1 秒
  初始化进行中，T2 的状态：RUNNABLE
  T1 静态代码块执行完
  T1 用上了 Slow
  T2 用上了 Slow

静态代码块只执行了一次，T2 一直等到 T1 初始化完才继续。所以静态代码块里不要做耗时操作，两个类的静态初始化也不要互相依赖，否则线程会被卡住，甚至死锁。

这个保证也给了一种不加锁的懒加载单例写法，静态内部类单例：

public class Singleton {
    private Singleton() { }
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

外部类加载时 Holder 不会初始化；第一次调用 getInstance() 读 Holder.INSTANCE，才触发 Holder 初始化、创建实例，而 JVM 保证这一步只发生一次。

上面的输出里，T2 在等待时状态是 RUNNABLE，而不是 BLOCKED 或 WAITING。用 jstack 看 T2（节选）：

“加载”阶段由类加载器完成。JDK 9 之后内置三个：

类加载器加载什么在 Java 里看到的是

程序接着沿 getParent() 往上走：应用类加载器的 parent 是平台类加载器，平台类加载器的 parent 是 null（启动类加载器）。这里的“父子”不是继承关系，而是每个加载器内部有一个 parent 字段，指向它的上级。

还有一条后面反复要用的规则：一个类的身份 = 全限定名 + 加载它的类加载器。同一份 .class 文件，被两个不同的类加载器加载，在 JVM 看来就是两个不同的类。

3.6 双亲委派

类加载器收到加载请求时，不是自己先动手，而是按这个顺序来：

  1. 先查自己是不是已经加载过这个类，加载过就直接返回。
  2. 没加载过，先把请求交给父加载器；父加载器也照此办理，一路交到最顶上的启动类加载器。
  3. 父加载器找不到这个类，才轮到自己去找（调用 findClass）。

就像新员工遇到问题先请示组长，组长再请示经理，上级能处理的上级处理；上级都处理不了，才一层层退回来自己办。ClassLoader.loadClass 的源码就是这三步（JDK 源码简化）：

protected Class<?> loadClass(String name, boolean resolve) {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);                       // ① 加载过就直接返回
        if (c == null) {
            try {
                if (parent != null) c = parent.loadClass(name, false);  // ② 先交给父加载器
                else c = findBootstrapClassOrNull(name);                 //    顶层交给启动类加载器
            } catch (ClassNotFoundException e) { }
            if (c == null) c = findClass(name);                   // ③ 上级都找不到，才自己找
        }
        return c;
    }
}

这么设计有两个好处：

  • 安全：核心类永远由启动类加载器加载。你自己写一个 java.lang.String 放在 classpath 上，加载请求一路交到启动类加载器，它先找到了 JDK 的 String，你的那个根本轮不到。
  • 不重复：同一个类只要上级加载过，下级就直接用上级的那份，不会出现两个“不同的” java.lang.Object。

自定义类加载器：继承 ClassLoader，重写 findClass，负责“自己去找”这一步（从某个目录、网络或加密文件里读出字节，再调用 defineClass）。这样前两步仍由父类的 loadClass 完成，双亲委派保留下来。

examples/TwoLoaders.java 写了一个从 plugin/ 目录读类的加载器，用两个实例 l1、l2 分别加载同一个 Greeter.class（它不在 classpath 上）。JDK 17 实测：

    [Greeter 被 loader-1 初始化]
    [Greeter 被 loader-2 初始化]
类名都是 Greeter 和 Greeter
c1 == c2             : false
c2.isInstance(g1)    : false
l1 再 loadClass 一次  : true
让 l1 加载 String     : null
c2.cast(g1)          : Cannot cast Greeter to Greeter
  • l1、l2 的父加载器是应用类加载器，它在 classpath 上找不到 Greeter，于是各自调用 findClass，得到两个不同的类。类名完全一样，c1 == c2 却是 false，类型转换报出 Cannot cast Greeter to Greeter。在 Tomcat 或热部署环境里看到这种报错，就要想到是两个类加载器各加载了一份。
  • 让 l1 加载 String，请求一路交到启动类加载器，返回的是 JDK 的 String（加载器显示为 null）。
深入一层JDK 9 模块化之后的委派

JDK 9 引入模块系统后，平台类加载器和应用类加载器的 loadClass 被改写过：收到请求时，先根据包名判断这个类属于哪个模块，如果属于某个已知模块，就直接交给负责那个模块的加载器，而不是机械地先问父加载器。核心类仍然只会由启动类加载器加载，所以双亲委派的两个好处没有变，学习时按 3.6 节的三步理解就够了。

3.7 什么时候要打破双亲委派

双亲委派有一个局限：上级看不见下级的类。启动类加载器只认识 JDK 核心类，classpath 上的类它找不到。下面几种场景因此要“打破”它：

  • SPI 与线程上下文类加载器：JDBC 的 DriverManager 在 java.sql 模块里，由平台类加载器加载；而 MySQL 驱动在 classpath 上，平台类加载器看不见。解决办法是让 JDK 的代码拿到线程上下文类加载器（Thread.currentThread().getContextClassLoader()，默认就是应用类加载器），用它去加载驱动。相当于上级把任务反过来委托给下级。
  • Tomcat 的类隔离：一个 Tomcat 里跑多个 Web 应用，它们可能依赖同一个库的不同版本。Tomcat 给每个应用一个独立的 WebappClassLoader，先在自己的 WEB-INF 里找，找不到再交给上级（JDK 核心类除外），这样各应用的类互不干扰。这需要重写 loadClass。
  • 热部署：一个类加载器不能把已经加载的类再加载一遍。要换成新版本的类，就丢掉旧的类加载器，new 一个新的加载器重新加载。旧的加载器和它加载的类没人引用了，才能被回收；如果一直被引用着，就会出现单元二的元空间溢出。

面试这样说

讲一下类加载的过程。
类的生命周期是加载、验证、准备、解析、初始化、使用、卸载，中间三个合称链接。加载是按全限定名找到字节流，在方法区建立类的结构，在堆里生成 Class 对象；验证检查字节码合法；准备给静态变量分配内存并设零值；解析把符号引用换成直接引用；初始化执行编译器生成的 <clinit>，按源码顺序执行静态赋值和静态代码块，父类先初始化。初始化是懒的，只有 new、读写静态字段、调静态方法、反射、初始化子类、启动主类这几种主动使用才会触发，而且 JVM 保证它线程安全、只执行一次。
什么是双亲委派？为什么这样设计？怎么打破？
类加载器收到请求，先查自己加载过没有，没有就委托给父加载器，一直到启动类加载器，父加载器找不到才自己加载。好处一是安全，核心类只能由启动类加载器加载，没法被同名类替换；二是避免重复加载。打破的场景主要有三个：JDBC 这类 SPI，核心库要加载 classpath 上的实现类，用线程上下文类加载器反向委托；Tomcat 为了隔离不同 Web 应用，让每个应用的加载器先自己加载；热部署要丢掉旧加载器重新加载。自定义加载器想保留双亲委派就重写 findClass，想打破就重写 loadClass。

自测

  1. 准备阶段和初始化阶段都会给静态变量赋值，有什么区别？
    准备阶段只分配内存并设零值（0、false、null），编译期常量例外，直接设成最终值；初始化阶段执行 <clinit>()，按源码顺序执行程序员写的静态赋值语句和静态代码块。
  2. PreparePuzzle 为什么输出 a = 1, b = 0？把 INSTANCE 那一行挪到最后会怎样？
    准备阶段 a、b 都是 0。初始化按源码顺序：先执行 INSTANCE = new Counter()，构造方法把 a、b 都加到 1；static int a; 没有赋值语句，a 保持 1；b = 0 又把 b 改回 0。挪到最后，先执行 b = 0，再执行构造方法，结果是 a = 1, b = 1。
  3. 通过子类访问父类的静态字段，子类会初始化吗？读一个 static final String 字面量常量呢？
    都不会。通过子类读父类声明的静态字段，只初始化声明它的父类。static final 的字面量是编译期常量，javac 编译时就把值抄进了使用方的常量池，运行时根本不碰那个类。但如果 static final 字段的值要运行时才能算出来（如 System.nanoTime()），读它就会触发初始化。
  4. Class.forName 和 ClassLoader.loadClass 有什么区别？
    Class.forName(name) 默认会初始化类，执行静态代码块；ClassLoader.loadClass(name) 只加载、不初始化。早年 JDBC 写 Class.forName("com.mysql.jdbc.Driver")，就是要触发驱动类的静态代码块把自己注册到 DriverManager。
  5. 两个类的全限定名相同，一定是同一个类吗？
    不一定。类的身份由全限定名 + 加载它的类加载器共同决定。TwoLoaders 里同一个 Greeter.class 被两个加载器各加载一次，c1 == c2 是 false，类型转换报 Cannot cast Greeter to Greeter。
  6. 自己写一个 java.lang.String 能替换掉 JDK 的吗？为什么？
    不能。按双亲委派，加载 java.lang.String 的请求会一路交给启动类加载器，它先找到 JDK 自带的 String，你写的那个永远轮不到。而且 JDK 也禁止用户的类加载器定义 java.* 包下的类，会抛 SecurityException。
  7. JDBC 加载驱动为什么要用线程上下文类加载器？
    DriverManager 在 java.sql 模块里，由平台类加载器（JDK 8 是启动类加载器）加载，而 MySQL 等驱动在 classpath 上。按双亲委派，上级加载器看不见下级的类，所以 JDK 的代码改用线程上下文类加载器（默认是应用类加载器）去加载驱动，相当于反向委托给下级。
  8. 自定义类加载器应该重写 findClass 还是 loadClass？
    想保留双亲委派就重写 findClass：loadClass 里已经实现了“先查缓存、再交给父加载器、最后调用 findClass”，你只负责最后一步把字节找出来并 defineClass。只有需要打破双亲委派（比如 Tomcat 先加载自己的类）时才重写 loadClass。

4.1 new 一个对象的五步

先看 new 编译成了什么。examples/NewObject.java 里有一行 NewObject o = new NewObject(42);，javap -c 输出：

0: new           #8                  // class NewObject
3: dup
4: bipush        42
6: invokespecial #13                 // Method "<init>":(I)V
9: astore_1

一行 Java 代码，在字节码里被拆成了两步：new 指令负责“造出一个空对象”，把它的引用压到操作数栈上；invokespecial <init> 负责“执行构造方法”。中间的 dup 把这个引用复制一份：构造方法用掉一份，剩下的一份由 astore_1 存进局部变量 o。展开来是五步：

  1. 类加载检查：检查这个类是否已经加载、初始化过，没有就先走一遍单元三的流程。
  2. 分配内存：对象需要多大，在类加载完成后就确定了（4.3 节），JVM 要在堆里划出这么一块。
  3. 初始化零值：把这块内存里的字段全部设成 0、false、null。所以成员变量不赋值也能用，而局部变量不赋值就用会编译报错。
  4. 设置对象头：写入 Mark Word（哈希码、GC 年龄、锁状态）和类型指针（这个对象是哪个类的）。
  5. 执行构造方法：按程序员写的代码给字段赋值。

前四步由 new 指令完成，第五步由 invokespecial 完成。两步之间，对象已经存在、字段却都是零值，这就是“半初始化对象”，也是双重检查锁单例要加 volatile 的原因（见 learn-juc 单元二）。

分配内存有两种方式，取决于堆是否规整：

  • 指针碰撞：用过的内存在一边，空闲的在另一边，中间一个指针当分界线，分配就是把指针往空闲那边挪一段。
  • 空闲列表：用过的和空闲的交错在一起，JVM 维护一张空闲块列表，分配时找一块够大的。

堆是否规整，取决于垃圾收集器回收后会不会整理内存（单元六）。Serial、Parallel、G1 这些会整理内存的收集器用指针碰撞，CMS 这种只清除、不整理的收集器用空闲列表。

4.2 并发分配：CAS 与 TLAB

指针碰撞有个问题：两个线程同时 new，都读到同一个指针位置，就会分到同一块内存。JVM 有两种办法：

  • CAS + 失败重试：用 CAS（先比较再交换的原子指令）挪指针，失败就重读重试。正确，但所有线程都在争同一个指针。
  • TLAB（线程本地分配缓冲区）：每个线程先从 Eden 里批量领一小块内存，专属自己。平时 new 对象只在自己的 TLAB 里挪自己的指针，完全不需要同步；TLAB 用完了，再用 CAS 领一块新的。

TLAB 就像每个人先从公共纸箱里领一叠便利贴：领的时候要排队，平时写一张撕一张，只动自己手里那叠。

TLAB 默认开启。examples/TlabBench.java 让 4 个线程各分配 2000 万个小对象：默认每轮约 120 到 150ms，加 -XX:-UseTLAB 关掉后每轮约 6300ms，慢了约 50 倍（JDK 17 实测）。所以 new 一个小对象的典型代价，就是在 TLAB 里挪一下指针再把内存清零，非常便宜。

4.3 对象的内存布局

一个对象在堆里分成三部分：

部分内容大小（64 位 JVM，默认开启压缩指针）
对象头Mark Word：哈希码、GC 分代年龄、锁状态8 字节
类型指针：指向方法区里的类元数据4 字节
数组长度（只有数组有）4 字节
实例数据各个字段，JVM 会重新排列顺序让对象更紧凑看字段

压缩指针：64 位 JVM 上，一个地址本来要 8 字节。HotSpot 默认用 4 字节存对象引用和类型指针。因为对象都按 8 字节对齐，地址最低 3 位永远是 0，4 字节的值左移 3 位就能表示 32GB 的范围。所以堆超过约 32GB 时压缩指针失效，每个引用变回 8 字节，同样的数据占的内存明显变多（实测上面那个四字段的类从 32 字节变成 40 字节）。把堆从 31GB 调到 33GB，能装下的对象可能反而更少。

4.4 对象的访问定位

栈帧里的引用怎么找到堆里的对象？有两种做法：

方式引用里存的是好处
句柄句柄池里一个句柄的地址，句柄再分别指向对象数据和类型数据GC 移动对象时只改句柄，引用不用改
直接指针对象的地址，对象头里有类型指针少一次间接访问，速度快

HotSpot 用的是直接指针：对象访问极其频繁，省一次间接访问很划算；代价是 GC 移动对象后，要把所有指向它的引用都改掉。

4.5 对象一定分配在堆上吗？逃逸分析

从 Java 语义上说，对象都在堆上。但 1.6 节的 JIT 编译热点代码时，会做逃逸分析：看一个对象的作用范围有没有“逃”出去。

  • 不逃逸：对象只在方法内部使用。
  • 方法逃逸：对象作为返回值或参数传到了别的方法。
  • 线程逃逸：对象被赋给了静态变量或其他线程能访问的字段。

对不逃逸的对象，C2 编译器可以做两项优化：

  • 标量替换：不创建对象，直接把它的字段拆成几个局部变量（“标量”）。对象根本不在堆上分配，也就不产生垃圾。
  • 锁消除：不逃逸的对象不会被别的线程访问，加在它上面的 synchronized 可以直接去掉。

逃逸分析依赖方法内联：JIT 把被调用的小方法直接嵌进调用方，才能看清一个对象在整段代码里有没有被传出去。

用实验证明：examples/EscapeDemo.java 循环调用 2 亿次 distance()，每次 new 一个只在方法里使用的 Point，并统计期间发生了几次 GC。JDK 17、-Xmx64m 实测（每种配置跑三轮，取第 2 轮）：

配置用时期间 GC 次数
默认（逃逸分析开启）171 ms0
-XX:-DoEscapeAnalysis644 ms121

2 亿个 16 字节的 Point 就是 3.2GB，堆只有 64MB，真要分配的话一定会 GC 很多次，关掉逃逸分析后正是这样。开着逃逸分析时一次 GC 都没有，说明这些 Point 根本没有在堆上分配。

回答这道题时注意三点：

  • 常说的“栈上分配”，HotSpot 并没有实现，效果是靠标量替换达到的。
  • 只有代码被 C2 编译后才生效，解释执行时照样在堆上分配。
  • “没有逃逸”只是可以优化的前提，不代表一定会被优化，比如方法太大没被内联，分析就做不了。

说一下对象的创建过程。
分五步。先做类加载检查，没加载就先加载类；然后分配内存，堆规整就用指针碰撞，否则用空闲列表，并发安全靠 CAS 重试和 TLAB，TLAB 是每个线程在 Eden 里预先领的一小块私有缓冲区，在里面分配不用同步；接着把内存清零，所以成员变量有默认值；然后设置对象头，写入 Mark Word 和类型指针；最后执行构造方法。前四步对应 new 指令，最后一步对应 invokespecial 调用 <init>。
对象的内存布局是怎样的？一个 Object 占多少字节？
对象由对象头、实例数据和对齐填充组成。对象头里是 Mark Word，存哈希码、GC 年龄和锁状态，8 字节；还有类型指针，开启压缩指针时 4 字节；数组再多 4 字节长度。整个对象按 8 字节对齐，所以 64 位 JVM 默认配置下 new Object() 是 12 字节对象头补齐到 16 字节。堆超过 32GB 时压缩指针失效，引用和类型指针变成 8 字节，对象会变大。
对象一定分配在堆上吗？什么是逃逸分析？
从语义上说对象都在堆上，但 JIT 会做逃逸分析，判断对象有没有逃出方法或线程。对没有逃逸的对象，C2 可以做标量替换，把字段拆成局部变量，不在堆上分配，也就没有 GC 压力，还可以做锁消除。HotSpot 并没有真正实现栈上分配，靠的是标量替换；而且只在 C2 编译后生效，没逃逸也不保证一定优化。我做过实验：循环 new 两亿个不逃逸的小对象，开着逃逸分析一次 GC 都没有，关掉后一百多次 GC，耗时是近四倍。

自测

  1. new 一个对象有哪五步？哪几步由 new 指令完成，哪一步由 invokespecial 完成？
    类加载检查、分配内存、初始化零值、设置对象头、执行构造方法。前四步由 new 指令完成，得到一个字段全是零值的对象；第五步由 invokespecial <init> 调用构造方法完成。
  2. 两个线程同时 new 对象，JVM 怎么保证它们分不到同一块内存？TLAB 为什么快？
    两种办法：用 CAS 移动分配指针，失败重试；或者用 TLAB，每个线程先从 Eden 里批量领一小块私有缓冲区，在里面分配只移动自己的指针，不需要任何同步，用完了才用 CAS 领新的一块。实测 4 个线程各分配 2000 万个小对象，开 TLAB 约 130ms，关掉要 6300ms 以上。
  3. 为什么成员变量不赋值也能用，局部变量不行？
    创建对象的第三步会把对象的内存全部清零，所以成员变量有默认值（0、false、null）；类的静态变量也在准备阶段被清零。局部变量在栈帧的局部变量表里，没有清零这一步，编译器要求先赋值再使用。
  4. new Object() 占多少字节？Long 呢？分别怎么算出来的？
    默认开启压缩指针时，new Object() 是 16 字节：Mark Word 8 + 类型指针 4 = 12 字节对象头，补齐到 8 的倍数。Long 是 24 字节：12 字节对象头 + 8 字节 long = 20，补齐到 24。
  5. 压缩指针是什么？为什么堆超过 32GB 时可能“装得更少”？
    64 位 JVM 默认用 4 字节存对象引用和类型指针。对象按 8 字节对齐，地址低 3 位总是 0，4 字节的值左移 3 位就能覆盖 32GB。堆超过约 32GB 后压缩指针失效，每个引用变回 8 字节，对象普遍变大（实测四字段的类从 32 字节变成 40 字节），所以堆调大一点，能装的对象反而可能更少。
  6. HotSpot 用句柄还是直接指针访问对象？各有什么好处？
    HotSpot 用直接指针：引用存对象地址，对象头里有类型指针，访问对象少一次间接跳转，速度快；代价是 GC 移动对象后要更新所有引用。句柄方式的引用指向句柄池，对象移动时只改句柄，引用不用动，但每次访问多一次间接访问。
  7. 什么样的对象会被判定为“没有逃逸”？标量替换做了什么？
    对象只在方法内部使用：没有作为返回值或参数传到别的方法，也没有被赋给静态变量或其他对象的字段。标量替换把这样的对象拆成几个局部变量（标量），不再创建对象，也就不在堆上分配、不产生垃圾。
  8. EscapeDemo 关掉逃逸分析后，GC 次数为什么从 0 变成了 121？
    开着逃逸分析时，C2 把 distance() 内联后发现 Point 没有逃出去，用标量替换把它拆成两个 int 局部变量，2 亿个 Point 一个都没在堆上分配，所以没有 GC。关掉后每个 Point 都真的在 Eden 分配，2 亿 × 16 字节约 3.2GB，64MB 的堆要反复 Young GC，一轮 121 次，耗时也变成近四倍。

垃圾判定

哪些对象可以回收

GC 不是去找垃圾，而是去找活对象：从 GC Roots 出发，顺着引用能走到的对象都活着，走不到的就是垃圾。

学完这个单元，你能

  • 说出强、软、弱、虚四种引用在 GC 时的区别和各自的用途。
  • 解释找 GC Roots 时为什么必须停下所有业务线程，以及线程为什么只能在安全点停下。

单元四讲了对象怎么出生，本单元讲对象怎么“被判死刑”。顺序是：先用实验否定最直观的引用计数（5.1），再讲 JVM 实际用的可达性分析（5.2），然后看四种引用怎么影响判定（5.3），补上方法区里的回收（5.4），最后看“找根”这一步为什么要停顿（5.5）。

5.1 引用计数法为什么不行

最直观的办法是给每个对象记一个引用计数：有一个地方引用它就加 1，引用断开就减 1，减到 0 就是垃圾。实现简单，判定也及时。但它解决不了循环引用：a 引用 b、b 引用 a，即使外界谁都不再引用它们，两者的计数也永远是 1。

JVM 用的是不是引用计数，跑一下就知道。examples/CycleRef.java 让两个各带 10MB 数据的对象互相引用，再去掉外部引用，然后调用 System.gc()。用弱引用当“探针”（弱引用不影响回收，对象被回收后 get() 返回 null，5.3 节讲）。JDK 17 加 -Xlog:gc 实测：

[0.003s][info][gc] Using G1
[0.018s][info][gc] GC(0) Pause Full (System.gc()) 28M->4M(40M) 1.368ms
a 被回收了吗：true
b 被回收了吗：true

堆从 28MB 降到 4MB，互相引用的两个对象连同 20MB 数据都被回收了。所以 HotSpot 判断对象死活用的不是引用计数。

5.2 可达性分析与 GC Roots

可达性分析：从一组叫 GC Roots 的起点出发，顺着对象之间的引用往下走，能走到的对象就是活的；走不到的，不管它们之间有没有互相引用，都是垃圾。

把它想成放风筝：GC Roots 是人手里攥着的线头，顺着线能牵到的风筝都还在天上；线断了的风筝，就算两只风筝绑在一起（循环引用），也一样会飞走。

哪些对象可以作为 GC Roots？ 简单说，就是“此刻一定还在用的东西”直接引用的对象：

  • 虚拟机栈中局部变量表引用的对象：正在执行的方法里的参数、局部变量。
  • 本地方法栈中 JNI 引用的对象。
  • 类的静态变量引用的对象。
  • 常量引用的对象，比如字符串常量池里的引用。
  • 被 synchronized 持有的对象（锁对象）。
  • JVM 内部的引用：基本类型对应的 Class 对象、常驻的异常对象、系统类加载器等。

回到 CycleRef：a = null; b = null; 之后，两个对象只剩彼此之间的引用，没有任何一条路从 GC Roots 通向它们，所以被判定为垃圾。

5.3 四种引用

只有“可达”和“不可达”两种状态，有些场景不够用：比如缓存，希望内存充足时留着，紧张时可以丢掉。所以 Java 把引用分成四种强度：

引用写法什么时候被回收典型用途
强引用Object o = new Object()只要强引用还在，宁可 OOM 也不回收绝大多数引用
软引用new SoftReference<>(obj)内存不够时（OOM 之前）才回收内存敏感的缓存
弱引用new WeakReference<>(obj)下一次 GC 就回收WeakHashMap、ThreadLocalMap 的 key
虚引用new PhantomReference<>(obj, queue)get() 永远返回 null；对象被回收后，引用本身被放进队列得知对象已被回收，清理堆外资源

examples/RefTypes.java 各用一种引用指向一个 8MB 的数组，先 GC 一次，再不停分配内存直到内存吃紧。JDK 17、-Xmx64m 实测：

GC 之前  强=true  软=true  弱=true  虚 get()=null
一次 GC  强=true  软=true  弱=false  虚引用进队列=true
内存吃紧（又分配了 36 MB）后  软=false
  • 一次普通的 GC：弱引用指向的数组被回收，虚引用的数组也被回收、引用进了队列；软引用的数组还在，因为内存还够。
  • 内存吃紧时：JVM 在抛 OOM 之前回收了软引用的数组。
  • 虚引用的 get() 从一开始就是 null，它不是用来访问对象的，而是用来收到“对象已经被回收”的通知。2.5 节的直接内存就是这样释放的：DirectByteBuffer 对象被回收后，JDK 通过虚引用（Cleaner）得知，再去释放对应的堆外内存。

ThreadLocal 的 key 用弱引用、以及由此引出的内存泄漏，见 learn-juc 单元九。

5.4 对象的“缓刑”与方法区的回收

finalize：重写了 finalize() 的不可达对象，会先被放进队列，等专门的线程调用一次 finalize()，对象甚至能在里面把自己重新挂到某个引用上“复活”。这个机制执行时机不确定、拖慢回收，JDK 9 起已经废弃，释放资源请用 try-with-resources。

方法区也会回收，但条件苛刻，收益也小：

  • 废弃常量：比如字符串常量池里一个没有任何地方引用的字符串。
  • 不再使用的类，要同时满足三个条件：

1. 这个类的所有实例都已经被回收；

2. 加载这个类的类加载器已经被回收；

3. 这个类的 Class 对象没有在任何地方被引用（比如反射）。

第二个条件决定了：由启动类、平台类、应用类加载器加载的类，基本不会被卸载，因为这些加载器一直活着。只有自定义类加载器加载的类才有机会卸载，这就是单元三说的“热部署要丢掉旧加载器”，也是元空间泄漏最常见的根源。

5.5 找根要停顿：STW 与安全点

可达性分析要从 GC Roots 出发，而 GC Roots 大量藏在各个线程的栈帧里。如果业务线程一边跑一边改引用，GC 刚找到的根下一刻可能就变了。所以至少在枚举 GC Roots 的那一刻，必须让所有业务线程停下来，这就是 Stop The World（STW）。

线程不能在任意一条指令上停下，只能停在安全点（safepoint）：

  • 在安全点上，JVM 预先记好了“栈帧里哪些位置存的是引用”（这张表叫 OopMap），GC 直接查表，不用扫描整个栈去猜。
  • 安全点设在方法调用、循环跳回、抛出异常这类位置。
  • 需要 STW 时，JVM 设一个标志；线程跑到最近的安全点时检查这个标志，发现要停就自己挂起。
  • 正在 sleep 或者等锁的线程不执行代码，没法“跑到”安全点。它们所在的代码段引用关系不会变化，叫安全区域：进入时声明一下，GC 就可以不等它；离开时检查 GC 是否完成，没完成就等着。

所以一次 STW 的时长 = 所有线程跑到安全点的时间 + GC 真正干活的时间。用 -Xlog:safepoint 能看到每次安全点的这两段时间（JDK 17 实测，节选）：

[0.017s][info][safepoint] Safepoint "G1TryInitiateConcMark", Time since last: 8187209 ns, Reaching safepoint: 10500 ns, At safepoint: 278083 ns, Total: 288583 ns

Reaching safepoint 是等线程到齐用的 10.5 微秒，At safepoint 是停下来干活的 278 微秒。线上偶尔会遇到某个线程迟迟跑不到安全点，所有线程都陪它干等，日志里的 Reaching safepoint 就会异常地大。

面试这样说

怎么判断一个对象可以被回收？哪些对象可以作为 GC Roots？
HotSpot 用可达性分析：从 GC Roots 出发顺着引用链往下走，走不到的对象就可以回收。不用引用计数，是因为它解决不了循环引用，两个互相引用的对象计数永远不为零。GC Roots 主要有：虚拟机栈里局部变量引用的对象、本地方法栈里 JNI 引用的对象、静态变量引用的对象、常量引用的对象、被 synchronized 持有的对象，以及 JVM 内部的引用比如系统类加载器。
强、软、弱、虚四种引用有什么区别？
强引用只要还在就不回收，宁可 OOM；软引用在内存不足、要抛 OOM 之前才回收，适合做缓存；弱引用下一次 GC 就回收，WeakHashMap 和 ThreadLocalMap 的 key 用的就是它；虚引用的 get 永远是 null，不影响对象的生命周期，作用是对象被回收后把引用放进队列通知我们，DirectByteBuffer 就靠它释放堆外内存。
什么是安全点？为什么 GC 要等线程到达安全点？
枚举 GC Roots 时引用关系不能变，所以要 STW。但线程不能随便停，只有在安全点上，JVM 才记录了栈帧里哪些位置是引用（OopMap），GC 才能准确找到根。安全点设在方法调用、循环回跳、异常跳转这些位置，线程跑到安全点时检查标志，主动挂起。sleep 或阻塞的线程处在安全区域，引用关系不会变，GC 不用等它们。

    会。可达性分析只看从 GC Roots 能不能走到，对象之间互相引用不影响判断，就像两只绑在一起的风筝，没人牵线一样会飞走。
  4. 软引用和弱引用分别在什么时候被回收？各举一个用途。
    软引用在内存不足、即将抛 OOM 之前才回收，适合做内存敏感的缓存（如图片缓存）；弱引用在下一次 GC 时就回收，用于 WeakHashMap 和 ThreadLocalMap 的 key。RefTypes 实测：一次普通 GC 后弱引用被清空、软引用还在；内存吃紧后软引用也被清空。
  5. 虚引用的 get() 永远返回 null，那它有什么用？
    它不是用来访问对象的，而是用来得知对象已经被回收：创建时关联一个 ReferenceQueue，对象被回收后虚引用会进入队列，程序据此做清理。DirectByteBuffer 就靠 Cleaner（基于虚引用）在对象被回收后释放堆外内存。
  6. 一个类满足什么条件才能被卸载？为什么我们自己写的业务类基本不会被卸载？
    三条同时满足：所有实例都已被回收；加载它的类加载器已被回收；它的 Class 对象没有在任何地方被引用。业务类由应用类加载器加载，这个加载器在程序运行期间一直活着，第二条永远不满足，所以基本不会卸载。只有自定义类加载器加载的类才有机会卸载。
  7. 枚举 GC Roots 时为什么必须 STW？线程为什么只能在安全点停下？
    GC Roots 大量在各线程的栈帧里，线程一边跑一边改引用，找到的根就不准确，所以枚举时要冻结引用关系，暂停所有业务线程。线程只能停在安全点，是因为只有在安全点上 JVM 才记录了栈帧里哪些位置存的是引用（OopMap），GC 才能准确地找到根；安全点设在方法调用、循环跳回、异常跳转等位置。
单元六

回收算法与分代

对象的一生

三种基础回收算法各有短板：标记-清除留碎片，复制浪费空间，标记-整理要搬家。分代就是按对象的寿命把堆分开，让每一块用最合适的算法。

学完这个单元，你能
  • 说出三种回收算法的过程和优缺点。
  • 讲清一个对象从 Eden 出生、在 Survivor 之间搬家、到晋升老年代的全过程，并在 GC 日志里认出这些变化。
  • 分清 Young GC、Mixed GC、Full GC，说出 Full GC 的常见触发原因。

单元五回答了“谁是垃圾”，本单元回答“垃圾怎么清”。顺序是：先看三种基础算法（6.1），再看为什么要按寿命分代（6.2），然后跟着 GC 日志看一个对象的一生（6.3），接着解决分代带来的跨代引用问题（6.4），最后把各种 GC 的名字理清楚（6.5）。

6.1 三种基础算法

算法做法优点缺点
标记-清除标记出活对象，把其余的空间回收简单，不移动对象留下内存碎片，大对象可能找不到连续空间；分配要用空闲列表
复制内存分成两半，只用一半；把活对象复制到另一半并紧凑排好，原来那一半整块清空没有碎片；只处理活对象，活得少时极快浪费一半空间；活对象多时复制成本高
标记-整理标记出活对象，把它们往一端挪，清掉边界以外的空间没有碎片，也不浪费空间要移动对象并更新所有引用，停顿更长

三种算法的取舍，归结起来就是一句话：活对象少，就用复制，搬几个活的走、整块清空最省事；活对象多，复制太贵，就用标记-清除或标记-整理。4.1 节说的“整理过的堆用指针碰撞，没整理的只能用空闲列表”，就是这里的结果。

6.2 分代：按寿命分区

大量统计表明两个规律：

  • 绝大多数对象朝生夕灭：方法里 new 的临时对象、一次请求里用的 DTO，用完就成了垃圾。
  • 熬过越多次 GC 的对象，越难死：缓存、连接池、Spring 的单例 Bean，会一直活到程序结束。

既然寿命差别这么大，就把堆分成两块，分别对待：

  • 新生代：存新对象，每次 GC 绝大部分都是垃圾、活下来的很少，正适合复制算法。
  • 老年代：存活得久的对象，每次 GC 大部分都还活着，复制不划算，用标记-清除或标记-整理。

新生代又分成一个 Eden 和两个 Survivor（S0、S1），默认比例 8:1:1（-XX:SurvivorRatio=8）。每次只用 Eden 和其中一个 Survivor，GC 时把活对象复制到另一个 Survivor。这样复制算法只“浪费”了 10% 的新生代，而不是一半。新生代和老年代的比例默认是 1:2（-XX:NewRatio=2），G1 会动态调整。

6.3 对象的一生

把规则串起来，一个对象从出生到“养老”是这样的：

  1. 在 Eden 出生：新对象在 Eden 分配（4.2 节的 TLAB 也在 Eden 里）。
  2. Eden 满了，触发 Minor GC（只回收新生代的 GC，也叫 Young GC）：把 Eden 和正在用的那个 Survivor（叫 from）里的活对象，复制到空着的那个 Survivor（叫 to），年龄加 1；然后清空 Eden 和 from，from 和 to 互换角色。
  3. 年龄到了阈值，晋升老年代：默认 15（-XX:MaxTenuringThreshold），因为对象头里的年龄只有 4 位（4.3 节）。
  4. 动态年龄判断：如果 Survivor 里某个年龄及以下的对象加起来超过了 Survivor 的一半，那么大于等于这个年龄的对象直接晋升，不用等到 15。
  5. Survivor 放不下，提前晋升：活对象太多，to 区装不下，放不下的直接进老年代。
  6. 大对象直接进老年代：很大的数组如果在 Survivor 之间来回复制，代价太高。Serial 等收集器可以用 -XX:PretenureSizeThreshold 设一个门槛；G1 有专门存放大对象的 Humongous 区（7.5 节）。

跟着 GC 日志看一次 Minor GC：examples/MinorGC.java 用 Serial 收集器和固定的小堆，让日志最容易读。新生代 10MB（Eden 8MB + 两个 Survivor 各 1MB），先分配三个 2MB 的数组 a1、a2、a3，再分配一个 4MB 的 a4。JDK 17 加 -Xlog:gc,gc+heap=info 实测（DefNew 是 Serial 的新生代，Tenured 是它的老年代）：

---- 已分配 a1、a2、a3 共 6MB，接下来分配 4MB 的 a4
[0.020s][info][gc,heap] GC(0) DefNew: 7127K(9216K)->453K(9216K) Eden: 7127K(8192K)->0K(8192K) From: 0K(1024K)->453K(1024K)
[0.020s][info][gc,heap] GC(0) Tenured: 0K(14336K)->6144K(14336K)
[0.020s][info][gc     ] GC(0) Pause Young (Allocation Failure) 6M->6M(23M) 1.066ms
---- a4 分配完成
  • Eden 里已有 7127K（a1 到 a3 共 6MB，加上 JVM 启动时自己创建的对象），放不下 4MB 的 a4，触发了一次 Young GC，原因是 Allocation Failure（分配失败）。
  • a1 到 a3 都还被引用着，是活对象，但 Survivor 只有 1MB，装不下 6MB，于是直接进了老年代：Tenured: 0K->6144K，正好 6MB。JVM 自己那 453K 小对象进了 Survivor（From）。
  • GC 后 Eden 清空，a4 顺利分配在 Eden。

再看年龄是怎么涨的：examples/Tenuring.java 让一个 128KB 的数组一直活着，同时不停地分配垃圾，触发多次 Minor GC。为了少等几轮，把晋升阈值设成 3，新生代 20MB（Survivor 各 2MB）。加 -Xlog:gc+age=trace 能看到 Survivor 里每个年龄有多少字节（JDK 17 实测，节选）：

GC(0) - age   1:     593280 bytes,     593280 total
GC(0) Tenured: 0K(20480K)->0K(20480K)
GC(1) - age   2:     593152 bytes,     700288 total
GC(2) - age   3:     593152 bytes,     700208 total
GC(3) Tenured: 0K(20480K)->579K(20480K)

这批 579K 的对象（128KB 的数组加上 JVM 自己的对象）在前三次 GC 里年龄从 1 涨到 3，一直待在 Survivor；第四次 GC 时到了阈值，搬进老年代，Tenured 从 0K 变成 579K。

动态年龄判断也能在日志里看到。同一个程序，把新生代缩小到 10MB（-Xmn10m，Survivor 各 1MB），第一次 GC 后活下来的 593280 字节超过了 Survivor 的一半（524288 字节），JVM 当场把阈值从 3 降到了 1：

GC(0) Desired survivor size 524288 bytes, new threshold 1 (max threshold 3)
GC(0) - age   1:     593280 bytes,     593280 total

空间分配担保：Minor GC 有可能把一大批对象推进老年代。所以每次 Minor GC 之前，JVM 先检查老年代的连续空闲空间，是否大于新生代所有对象的总大小，或者大于历次晋升到老年代的平均大小。不满足就说明“担保”不住，先做一次 Full GC 腾出老年代。

6.4 跨代引用：Young GC 为什么不用扫整个老年代

只回收新生代时有个麻烦：新生代对象可能只被某个老年代对象引用着。只从 GC Roots 出发、只看新生代，会把它误判成垃圾；可要是每次 Young GC 都把老年代扫一遍，分代就失去了意义。

解决办法是记忆集：另外记下“老年代里哪些地方有指向新生代的引用”，Young GC 时只看这些地方。HotSpot 里的具体实现叫卡表（Card Table）：

  • 把老年代按 512 字节切成一张张“卡”，卡表是一个字节数组，每个字节对应一张卡。
  • 每当程序把一个引用写进某个对象的字段，JVM 在这次赋值之后自动执行一小段代码，叫写屏障。如果这次写入让老年代的对象引用了新生代对象，写屏障就把那张卡标成“脏”。
  • Young GC 时，只扫描脏卡里的老年代对象，把它们当作额外的 GC Roots。

这是“用一点写入时的开销，换 GC 时少扫一大片”。写屏障在单元七还会反复出现。

6.5 GC 的种类：Young、Mixed、Full

名称回收范围谁有
Young GC（Minor GC）只回收新生代所有分代收集器
Old GC只回收老年代只有 CMS 的并发回收
Mixed GC整个新生代 + 一部分老年代只有 G1
Full GC整个堆 + 方法区所有收集器

“Major GC”这个说法含义不统一，有人指 Old GC，有人指 Full GC，听到时先问清楚指的是哪个。

Full GC 的常见触发原因：

  • 老年代空间不够：对象晋升或大对象分配时放不下。
  • 空间分配担保失败（6.3 节）。
  • 元空间不够了。
  • 代码里调用了 System.gc()。5.1 节的日志里那次 Pause Full (System.gc()) 就是它触发的。
  • 并发收集器回收的速度跟不上分配的速度，只好停下来做一次 Full GC（7.4、7.5 节）。

Full GC 要处理整个堆，停顿通常比 Young GC 长得多。7.7 节的实测里，Serial 收集器的一次 Full GC 停了 466ms。线上频繁 Full GC 的排查方法见 8.5 节。

面试这样说

垃圾回收算法有哪些？各有什么优缺点？
有三种基础算法。标记-清除是标记活对象后清掉其余空间，简单但会留碎片；复制是把内存分两半，活对象复制到另一半后整块清空，没有碎片、活对象少时很快，但浪费空间；标记-整理是把活对象往一端挪，没有碎片也不浪费，但要移动对象、停顿更长。实际使用的是分代收集：新生代对象朝生夕灭，用复制算法，并用 Eden 加两个 Survivor 按 8:1:1 划分，只浪费 10%；老年代对象存活率高，用标记-清除或标记-整理。
对象什么时候进入老年代？
对象先在 Eden 分配，Minor GC 后活下来的复制到 Survivor，年龄加一，以后每熬过一次 Minor GC 再加一，到阈值（默认 15）就晋升老年代。另外几种情况会提前进入：Survivor 里相同年龄及以下的对象超过一半时，大于等于该年龄的直接晋升；Survivor 放不下的活对象直接进老年代；大对象直接分配在老年代，G1 里则放进 Humongous 区。
Minor GC 和 Full GC 有什么区别？什么时候会触发 Full GC？
Minor GC 只回收新生代，Eden 满了就触发，借助卡表不用扫整个老年代，通常很快；Full GC 回收整个堆和方法区，停顿长得多。Full GC 的常见原因有：老年代放不下晋升的对象或大对象、空间分配担保失败、元空间不足、调用了 System.gc()，以及 CMS、G1 这类并发收集器回收速度跟不上分配速度。

自测

  1. 标记-清除、复制、标记-整理各有什么缺点？
    标记-清除会留下内存碎片，大对象可能找不到连续空间，分配也只能用空闲列表；复制要浪费一部分空间，活对象多时复制成本高；标记-整理要移动对象并更新所有引用，停顿更长。
  2. 新生代为什么用复制算法？为什么要分 Eden 和两个 Survivor，而不是对半分？
    新生代的对象绝大多数朝生夕灭，每次 GC 活下来的很少，复制算法只需要搬这一小部分活对象，然后整块清空，又快又没有碎片。既然活下来的很少，就不需要留一半空间：Eden 加两个 Survivor 按 8:1:1 划分，每次只用 Eden 和一个 Survivor，只“浪费”10%。
  3. 对象晋升老年代有哪几种情况？
    年龄达到阈值（默认 15）；动态年龄判断：Survivor 中某个年龄及以下的对象超过 Survivor 一半时，大于等于该年龄的直接晋升；Minor GC 时 Survivor 放不下的活对象提前晋升；大对象直接在老年代分配（G1 放进 Humongous 区）。
  4. 年龄阈值默认为什么是 15？
    对象的 GC 年龄记在对象头的 Mark Word 里，只占 4 个比特，最大能表示 15。所以 MaxTenuringThreshold 最大也只能设到 15。
  5. MinorGC 的日志里，Tenured: 0K->6144K 说明发生了什么？
    这次 Minor GC 有 6MB 对象进入了老年代。a1、a2、a3 三个 2MB 数组都还活着，但 Survivor 只有 1MB 装不下，于是没有经过 Survivor，直接提前晋升到老年代。Eden 清空后，4MB 的 a4 才分配成功。
  6. Young GC 时，老年代对象引用了新生代对象，怎么避免扫描整个老年代？
    用记忆集，HotSpot 的实现是卡表：老年代按 512 字节切成卡，每次给对象的引用字段赋值后，写屏障检查这次写入是否让老年代对象引用了新生代对象，是的话把对应的卡标脏。Young GC 时只扫描脏卡里的老年代对象，把它们当作额外的 GC Roots。
  7. 哪些情况会触发 Full GC？
    老年代空间不足（晋升或大对象放不下）；空间分配担保失败；元空间不足；代码调用了 System.gc()；CMS、G1 等并发收集器回收速度跟不上分配速度（并发失败、晋升失败）。

垃圾收集器

从 Serial 到 ZGC

收集器的演进只做一件事，把 STW 越切越短：从“全停下来一起扫”到“边跑边扫，只停一小下”，代价是更复杂的屏障、更多的 CPU 和内存。

学完这个单元，你能
  • 说出主流收集器的分工、算法和适用场景，以及 JDK 8、17、21 的默认收集器。
  • 讲清三色标记为什么会漏标，以及 CMS 和 G1 分别怎么解决。
  • 根据堆大小、延迟要求和 JDK 版本选择收集器，并说出低停顿收集器的代价。

单元六讲的是算法，本单元讲把算法落地的“收集器”。顺序是：先定下评价收集器的三个指标（7.1），再看只会 STW 的串行、并行收集器（7.2），然后解决“边跑边标记”带来的漏标难题（7.3），在此基础上看 CMS（7.4）、G1（7.5）、ZGC（7.6），最后用同一个负载实测对比，并给出选择建议（7.7）。

7.1 三个指标：吞吐量、停顿时间、内存占用

  • 吞吐量：业务代码运行时间占总时间的比例。批处理任务最在乎它。
  • 停顿时间：单次 STW 有多长。接口服务最在乎它，一次 500ms 的停顿就可能让请求超时。
  • 内存占用：为了回收，额外需要多少内存（记忆集、预留空间等）。

三者很难同时做到最好。好比打扫房间：把人全赶出去一口气扫完，扫得最快（吞吐高），但大家在门外等得久（停顿长）；让大家照常住着、清洁工见缝插针地扫，没人需要等（停顿短），但清洁工要多雇几个，还得一直盯着大家又扔了什么（CPU 和屏障开销）。

7.2 串行与并行：Serial、ParNew、Parallel

收集器区域算法回收时特点
Serial新生代复制单线程，STW最简单，额外开销最小
Serial Old老年代标记-整理单线程，STW和 Serial 搭配
ParNew新生代复制多线程，STWSerial 的多线程版，以前专门配合 CMS，随 CMS 一起退场
Parallel Scavenge新生代复制多线程，STW关注吞吐量，可自动调节各区大小
Parallel Old老年代标记-整理多线程，STW和 Parallel Scavenge 搭配，JDK 8 的默认组合

这几个收集器回收时都要 STW。多线程只是让停顿变短，并没有消除停顿，而且停顿时间随堆增大而增长：要扫描、复制的对象越多，停得越久。

7.3 并发标记的难题：三色标记与漏标

想缩短停顿，最耗时的“标记”就得和业务线程并发进行。描述并发标记的标准模型是三色标记：

  • 白色：还没被访问过。标记结束时还是白色的，就是垃圾。
  • 灰色：自己已经被访问到，但它引用的对象还没扫完。
  • 黑色：自己和它引用的对象都扫完了。

标记从 GC Roots 开始，把根直接引用的对象染灰，然后不断取一个灰色对象，把它引用的白色对象染灰，自己染黑，直到没有灰色对象。

问题出在业务线程一边跑一边改引用。看一个具体场景：引用链是 GC Roots → A → B → C，GC 线程在标记，业务线程同时执行了两行代码。

步骤发生了什么ABC
1GC：开始并发标记白白白
2GC：扫描 A，发现 B，A 扫完黑灰白
3业务线程：A.ref = C，A 新增了一条指向 C 的引用黑灰白
4业务线程：B.ref = null，删掉 B 指向 C 的引用黑灰白
5GC：扫描 B，B 没有引用了；没有灰色对象，标记结束黑黑白
6GC：回收白色对象黑黑回收

读这张表抓住三点：

  • 第 2 步之后 A 已经是黑色，GC 不会再回头扫它，所以第 3 步新增的 A → C 没人发现。
  • 第 4 步删掉 B → C 之后，GC 手里再也没有能通向 C 的路。
  • 两件事缺一件，C 都不会出错：只有第 3 步，第 5 步扫 B 时照样能找到 C；只有第 4 步，C 确实没人引用了，回收它是对的。

可 C 明明还被 A 引用着，业务线程下次读 A.ref 就会读到已经释放的内存。把这个场景归纳一下，活对象被当成垃圾回收，叫漏标，它要两个条件同时发生：

  1. 一个黑色对象新增了一条指向某个白色对象的引用（第 3 步）。黑色对象不会再被扫描，这条新引用没人发现。
  2. 所有灰色对象到这个白色对象的引用都被删掉了（第 4 步）。原本能顺着灰色对象找到它，现在路断了。

7.4 CMS：第一款并发收集器

CMS（Concurrent Mark Sweep）是老年代收集器，用标记-清除算法，目标是缩短停顿。它分四步：

  1. 初始标记（STW）：只标记 GC Roots 直接引用的对象，很快。
  2. 并发标记：顺着引用链标记整个老年代，和业务线程同时运行，耗时最长。
  3. 重新标记（STW）：处理并发标记期间增量更新记下的对象。
  4. 并发清除：清掉没被标记的对象，和业务线程同时运行。

最耗时的两步都和业务线程并发，所以停顿短。它的问题也很明显：

  • 内存碎片：标记-清除不整理，碎片多了，大对象找不到连续空间，只能来一次 Full GC 整理。
  • 浮动垃圾和预留空间：并发清除时业务线程还在分配对象，所以老年代不能等满了才回收，要提前留出空间。留的空间不够用，就会发生“并发失败”（Concurrent Mode Failure），退化成单线程的 Serial Old 做 Full GC，停顿反而更长。
  • 抢 CPU：并发阶段要占用一部分 CPU 核心，核数少时对业务影响明显。

CMS 在 JDK 9 被标记为废弃，JDK 14 被移除。

7.5 G1：把堆切成 Region

G1（Garbage First）是 JDK 9 起的默认收集器，目标是在可控的停顿时间内获得尽可能高的吞吐量。

Region：G1 不再把堆切成固定的新生代和老年代，而是切成大约 2048 个大小相同的 Region，每个 1MB 到 32MB（2 的幂）。每个 Region 在不同时刻扮演不同角色：Eden、Survivor、Old，或者 Humongous（存放超过半个 Region 的大对象，一个放不下就占连续的多个）。新生代和老年代只是“一组 Region”的逻辑名称，大小可以动态调整。Region 大小由堆大小决定：这台机器默认最大堆 6GB，Region 是 4MB；-Xmx256m 时是 1MB。

停顿可预测：用 -XX:MaxGCPauseMillis 设一个停顿目标（默认 200ms）。G1 记录每个 Region 里有多少垃圾、回收它要花多久，每次只挑回收价值最高（垃圾最多）的若干个 Region，在目标时间内回收。“Garbage First”的名字就是这么来的。

G1 的三种活动：

  1. Young GC（STW）：Eden 用完时触发，把所有 Eden 和 Survivor Region 里的活对象复制到新的 Survivor 或 Old Region。
  2. 并发标记：堆占用超过阈值（默认 45%）时启动。初始标记搭 Young GC 的便车，然后并发标记，再经过两个很短的 STW 阶段：最终标记（Remark）处理 SATB 记录，清理（Cleanup）统计每个 Region 的存活情况。
  3. Mixed GC（STW）：回收所有新生代 Region，外加一部分垃圾最多的老年代 Region。

回收速度跟不上分配速度时，G1 也会退化成 Full GC。

7.7 节实测的 G1 日志里，这三种活动依次出现（节选）：

GC(14) Pause Young (Concurrent Start) (G1 Evacuation Pause) 1262M->1118M(2048M) 22.242ms
GC(15) Pause Remark 1390M->1390M(2048M) 0.300ms
GC(21) Pause Young (Mixed) (G1 Evacuation Pause) 1683M->1444M(2048M) 10.250ms

Concurrent Start 是顺带做了初始标记的 Young GC；Remark 是并发标记里的短暂停顿，只有 0.3ms；Mixed GC 在日志里写作 Pause Young (Mixed)，比普通 Young GC 多回收了一部分老年代。

和 CMS 相比，G1 回收时把活对象从一个 Region 复制到另一个，整体上相当于标记-整理，没有碎片问题。代价是更多的内存：每个 Region 都有自己的记忆集，记录“谁引用了我”。8.5 节的本地内存统计里，一个 256MB 堆的进程，GC 自己的数据结构就占了约 55MB。

7.6 ZGC：停顿不超过 1 毫秒

ZGC 的目标是：无论堆多大（从几百 MB 到 16TB），停顿都不超过 1 毫秒。前面的收集器里，“移动对象”（复制、整理）都必须 STW，因为对象一挪，所有指向它的引用都要改，业务线程不能在这时去读。ZGC 做到了并发整理：业务线程运行的同时搬动对象。靠的是两样东西：

  • 染色指针：把 GC 需要的状态（这个对象标记过没有、是否已经被搬走）直接存在 64 位引用的几个高位上，而不是存在对象头里。
  • 读屏障：业务线程每次从堆里读出一个引用，JVM 都插入一小段检查。如果发现指针的“颜色”表明对象已经被搬走，就顺手把引用改成新地址，下次再读就不用检查了（叫“自愈”）。

这样，搬家可以慢慢并发地做，谁先读到旧地址，谁就顺手修正。只剩三个极短的 STW 阶段，只处理 GC Roots，与堆的大小无关。7.7 节实测中，ZGC 的三种停顿共 151 次，最长的一次是 0.021ms：

GC(0) Pause Mark Start 0.003ms
GC(0) Pause Mark End 0.008ms
GC(0) Pause Relocate Start 0.008ms

版本：JDK 11 实验性引入，JDK 15 可用于生产；JDK 21 加入分代 ZGC（-XX:+UseZGC -XX:+ZGenerational），JDK 23 起分代成为默认，JDK 24 移除了不分代的模式。

代价：

  • 读屏障让每次读引用都多一点开销，吞吐量通常比 G1 低一些。
  • 染色指针占用了引用的高位，不能用 4.3 节的压缩指针，同样的对象占内存更多。
  • 回收速度跟不上分配速度时，ZGC 会让分配对象的线程停下来等，叫 Allocation Stall。同一个测试负载把堆从 2GB 缩到 1GB，JDK 17 的 ZGC 日志里就出现了 Allocation Stall (main) 57.635ms：GC 本身的停顿仍然不到 1ms，业务线程却被卡了 57ms。所以用 ZGC 要给堆留足余量。

Shenandoah 是 Red Hat 开发的另一款并发整理收集器，思路相近，包含在 OpenJDK 里（Oracle JDK 不带）。

面试这样说

CMS 和 G1 有什么区别？
CMS 只管老年代，用标记-清除，分初始标记、并发标记、重新标记、并发清除四步，最耗时的两步和业务线程并发，所以停顿短；但它会产生碎片，并发失败时退化成单线程 Full GC，JDK 14 已被移除。G1 把堆切成大小相等的 Region，每个 Region 可以是 Eden、Survivor、Old 或 Humongous，新生代老年代只是逻辑上的一组 Region；它能设置停顿目标，每次挑垃圾最多的 Region 回收，Region 之间用复制，整体上没有碎片。代价是每个 Region 要维护记忆集，内存开销更大。JDK 9 起 G1 是默认收集器。
并发标记时应用还在修改引用，怎么避免漏标？
用三色标记来描述：白色没访问，灰色访问了但引用没扫完，黑色全部扫完。漏标需要同时满足两个条件：黑色对象新增了指向白色对象的引用，并且灰色对象到这个白色对象的引用全被删了。破坏任意一个就行：CMS 用增量更新，黑色对象新增引用时用写屏障记下来，重新标记时再扫一遍；G1 用原始快照 SATB，删除引用时把旧引用记下来继续扫。代价是会产生浮动垃圾，留到下次回收。
垃圾回收的哪些阶段会 STW？
枚举 GC Roots 一定要 STW，所以所有收集器都有停顿。Serial、Parallel 整个回收过程都 STW，只是 Parallel 用多线程缩短了时间；CMS 的初始标记和重新标记要 STW，并发标记和并发清除不用；G1 的 Young GC 和 Mixed GC 复制对象时要 STW，并发标记中只有初始标记（搭 Young GC 的车）、最终标记和清理三个短暂停顿；ZGC 连移动对象都是并发的，只剩几个只处理 GC Roots 的极短停顿。
ZGC 为什么停顿这么短？和 G1 有什么区别？
停顿长主要是因为移动对象时要停下业务线程。ZGC 用染色指针加读屏障实现了并发整理：GC 状态存在引用的高位，业务线程读引用时读屏障检查颜色，发现对象被搬走了就顺手修正指针，所以搬对象可以和业务并发。只剩几个只处理 GC Roots 的极短停顿，和堆大小无关，一般在 1 毫秒以内。和 G1 比，G1 追求吞吐和停顿的平衡，Young GC 和 Mixed GC 复制对象时仍要停下业务线程，停顿是几十毫秒级；ZGC 把停顿压到最低，代价是读屏障降低一些吞吐，不能用压缩指针，而且回收跟不上分配时会让分配线程停下来等，所以要留足堆空间。

自测

  1. 吞吐量和停顿时间为什么很难同时做到最好？
    要停顿短，就得把 GC 工作拆成很多小段或者和业务线程并发执行，这需要写屏障、读屏障、重新标记等额外工作，并且并发阶段要占用 CPU，总的 GC 开销变大，吞吐量下降；反过来，一次停下来集中回收效率最高、吞吐最好，但单次停顿长。
  2. 三色标记中，漏标需要同时满足哪两个条件？增量更新和 SATB 各破坏了哪一个？
    条件一：黑色对象新增了一条指向白色对象的引用；条件二：所有灰色对象到这个白色对象的引用都被删除了。增量更新（CMS）破坏条件一：记录黑色对象新增的引用，重新标记时再扫一遍；SATB（G1）破坏条件二：记录被删除的旧引用，把它们当作灰色继续扫。
  3. CMS 有哪几个阶段？哪几个要 STW？它有什么缺点？
    初始标记（STW）、并发标记、重新标记（STW）、并发清除。缺点：标记-清除产生碎片；并发清除期间产生浮动垃圾，要预留空间，预留不够会并发失败，退化成单线程 Serial Old 做 Full GC；并发阶段占用 CPU。JDK 14 已移除。
  4. G1 的 Region 有哪几种角色？大对象放在哪？
    Eden、Survivor、Old、Humongous，同一个 Region 在不同时刻可以扮演不同角色。超过半个 Region 大小的对象放进 Humongous Region，一个放不下就占用连续的多个。
  5. G1 怎么做到“停顿时间可预测”？
    把堆切成 Region，回收以 Region 为单位；通过 -XX:MaxGCPauseMillis 设停顿目标（默认 200ms），G1 统计每个 Region 的垃圾量和回收耗时，每次只挑回收价值最高的若干个 Region，保证在目标时间内完成。
  6. 垃圾回收的哪些阶段会 STW？
    枚举 GC Roots 一定要 STW。Serial、Parallel 整个回收过程都 STW；CMS 的初始标记、重新标记 STW，并发标记、并发清除不停；G1 的 Young GC、Mixed GC 复制对象时 STW，并发标记中只有初始标记、最终标记（Remark）、清理（Cleanup）三个短暂停顿；ZGC 连移动对象都并发，只剩三个只处理 GC Roots 的极短停顿（实测最长 0.021ms）。
  7. ZGC 是怎么在业务线程运行的同时移动对象的？
    靠染色指针和读屏障。GC 状态存在 64 位引用的高位上；业务线程每次从堆里读引用时，读屏障检查指针的颜色，如果对象已经被搬走，就把引用修正为新地址（自愈）。这样对象可以在业务线程运行时并发搬动，STW 只剩几个只处理 GC Roots 的极短阶段。
  8. GC 停顿只有零点几毫秒的 ZGC，为什么也可能让业务线程卡住几十毫秒？
    ZGC 回收是并发的，如果业务分配对象的速度超过回收速度，堆被用光，分配对象的线程只能停下来等 GC 腾出空间，这叫 Allocation Stall。它不算 GC 停顿，但业务线程同样被卡住。实测把堆从 2GB 缩到 1GB，日志里出现了 57ms 的 Allocation Stall。所以用 ZGC 要留足堆空间。
  9. JDK 8、JDK 17 的默认收集器分别是什么？一个只分了 1 个 CPU 的容器里呢？
    JDK 8 默认 Parallel（Parallel Scavenge + Parallel Old）；JDK 9 起包括 JDK 17 默认 G1。但只有在“服务器级机器”（至少 2 个 CPU、约 1.8GB 以上内存）上才默认 G1，只有 1 个 CPU 的容器里默认是 Serial。可以用 java -XX:+PrintCommandLineFlags -version 查看。

这次回收后堆反而多了 1M：程序刚启动，所有对象都还活着，而 GC 期间分配的新对象也算了进去。看 GC 日志时主要看四件事：多久一次、每次停多久、回收后堆的占用是否越来越高、Full GC 是什么原因触发的。“回收后的占用”一路上涨，就是内存泄漏的信号。

8.3 内存泄漏与 OOM

排查步骤：

  1. 确认是哪块内存：先看 OOM 的提示信息（2.6 节的速查表）。
  2. 看趋势：用 jstat 或 GC 日志观察老年代在 GC 之后的占用。正常应用是锯齿形，回收后回到差不多的水位；泄漏是水位一路上涨。
  3. 取证：隔一段时间做两次 GC.class_histogram 对比，看哪个类的实例数一直在涨；或者做一次堆转储。最好用 -XX:+HeapDumpOnOutOfMemoryError 让 JVM 在出事那一刻自动转储。
  4. 分析：用 MAT 打开堆转储。Histogram 看哪个类占得多；Dominator Tree 看哪个对象“支配”了最多的内存（它被回收，这些内存就能释放）；对可疑对象用 Path to GC Roots 查是谁引用着它不放。
  5. 修复并验证：改完后用同样的方式观察，确认老年代水位不再上涨。

拿 examples/LeakDemo.java 走一遍。它模拟一个只进不出的缓存：每个“请求”往静态 HashMap 里放一条 1KB 的记录，从来不删。用 -Xmx256m 启动，再用 jps -l 找到进程号，jstat -gcutil -t <pid> 15000 每 15 秒采样一次，JDK 17 实测（节选，Timestamp 是进程启动后的秒数）：

常见的泄漏来源：当缓存用的静态集合没有淘汰策略；线程池里的 ThreadLocal 用完没有 remove（learn-juc 单元九）；注册了监听器、回调却从不注销；连接、流没有关闭；自定义类加载器被引用着导致类卸载不掉（元空间泄漏）。

8.4 CPU 飙高

Linux 上的经典四步：

  1. top 找到 CPU 最高的 Java 进程，记下进程号 pid。
  2. top -Hp <pid> 列出这个进程里的线程，找到 CPU 最高的线程号 tid。
  3. printf '%x\n' <tid> 把线程号转成十六进制。
  4. jstack <pid> | grep -A 20 'nid=0x<十六进制>'：jstack 里每个线程的 nid 就是操作系统线程号，找到它的栈，就看到它在执行哪段代码。

JDK 11 起，jstack 还会在每个线程后面打印它累计用了多少 CPU 时间（cpu=），所以不依赖 top -H 也能定位：隔几秒打两次 jstack，cpu= 涨得最快的线程就是元凶。这个办法在 macOS、Windows 上同样适用。

examples/CpuHog.java 启动了三个睡觉的线程和一个死循环线程 order-calc。ps 显示进程 CPU 占用 99.2%。启动 3 秒和 8 秒时各打一次 jstack（JDK 17 实测，节选）：

"order-calc" #17 prio=5 os_prio=31 cpu=3186.60ms elapsed=3.20s ... runnable

# 5 秒后
"idle-1" #14 prio=5 os_prio=31 cpu=0.14ms elapsed=8.31s ... waiting on condition

5 秒里 order-calc 用掉了约 5100ms 的 CPU，相当于一个核被它占满；idle-1 几乎没动。它的栈顶是 CpuHog.spin 方法里的那个死循环，问题定位到了代码行。

CPU 飙高的常见原因：

  • 死循环，或者正则表达式的回溯爆炸。
  • 频繁 GC：GC 线程占满 CPU。top -H 里看到名为 GC Thread#0 这类的线程最忙时，转去看 jstat 和 GC 日志。
  • 大量计算、序列化，或者锁竞争激烈时线程反复自旋。

8.5 频繁 GC 与堆外内存

Young GC 频繁：对象分配得太快，或者新生代太小。先看是不是代码里产生了大量不必要的临时对象（比如循环里拼字符串、反复装箱），再考虑增大新生代。

Full GC 频繁：老年代总是被填满。按可能性排查：

  • 内存泄漏（8.3 节）：回收后老年代水位越来越高。
  • 新生代太小，对象还没来得及死就被提前晋升到老年代（6.3 节）。
  • 大对象太多，直接进入老年代。
  • 元空间不足。
  • 代码或第三方库调用了 System.gc()。可以用 -XX:+DisableExplicitGC 禁掉，但要小心：直接内存用满时，JDK 会调用 System.gc() 来回收那些 DirectByteBuffer（2.5 节），禁掉后可能变成直接内存溢出。

堆没满，进程内存却很高：Java 进程占的内存远不止堆。给 LeakDemo 加上 -XX:NativeMemoryTracking=summary，用 jcmd <pid> VM.native_memory summary 查看（JDK 17 实测，节选）：

Total: reserved=1751798KB, committed=267510KB
-                 Java Heap (reserved=262144KB, committed=140288KB)
-                     Class (reserved=1048664KB, committed=216KB)
-                    Thread (reserved=49498KB, committed=49498KB)
-                      Code (reserved=247738KB, committed=7626KB)

committed 是实际占用的部分：进程一共占了约 261MB，堆只占 137MB，GC 自己的数据结构（G1 的记忆集等，7.5 节）占了 54MB，线程栈占了 48MB。此外还可能有直接内存，以及 JNI 库自己申请的内存。

所以在容器里，-Xmx 不能设成容器的内存上限，否则堆没满，进程就因为超出容器限制被系统杀掉。常见做法是把堆设成容器内存的 70% 到 75%，或者用 -XX:MaxRAMPercentage=75.0 让 JVM 按比例自动计算（JDK 8u191 及以后、JDK 10 及以后能识别容器的内存限制）。

8.6 调优思路

先排查，后调参。大多数“JVM 问题”其实是代码问题：泄漏、不必要的对象、过大的查询结果。调参之前先回答三个问题：

  1. 是不是 GC 的问题？看 GC 日志和 jstat，用数据说话，而不是感觉“可能是 GC”。
  2. 目标是什么？吞吐量、停顿时间、还是内存占用？三者要取舍（7.1 节）。
  3. 改一处，测一次：一次只改一个参数，在同样的压力下对比改动前后的指标。

常用参数：

参数作用
-Xms、-Xmx初始堆、最大堆，服务端常设成一样
-Xmn新生代大小（用 G1 时不建议固定，会干扰它的停顿目标）
-Xss每个线程的栈大小
-XX:MetaspaceSize、-XX:MaxMetaspaceSize元空间第一次触发 GC 的阈值、元空间上限
-XX:MaxDirectMemorySize直接内存上限
-XX:+UseG1GC、-XX:+UseZGC选择收集器
-XX:MaxGCPauseMillisG1 的停顿时间目标
-XX:+HeapDumpOnOutOfMemoryError、-XX:HeapDumpPathOOM 时自动转储堆
-Xlog:gc*:file=...打开 GC 日志
-XX:MaxRAMPercentage在容器里按内存比例设置最大堆

想知道一个参数的默认值和最终生效值，用 java -XX:+PrintFlagsFinal -version | grep <参数名>。2.2 节的默认堆大小、1.4 节的默认栈大小，都是这样查出来的。

面试这样说

线上 CPU 飙高怎么排查？
先用 top 找到 CPU 最高的 Java 进程，再用 top -Hp 找到进程里 CPU 最高的线程，把线程号转成十六进制，在 jstack 输出里按 nid 找到这个线程，看它的栈停在哪段代码。最好隔几秒多打几次 jstack，确认一直停在同一个地方；JDK 11 以后 jstack 直接带每个线程的 cpu 时间，对比两次就能找到最忙的线程。如果最忙的是 GC 线程，就转去看 jstat 和 GC 日志，按频繁 GC 来查。常见原因有死循环、正则回溯、频繁 GC、锁竞争自旋。
线上 GC 很频繁，怎么排查？
先分清是 Young GC 还是 Full GC 频繁，用 jstat -gcutil 看 YGC、FGC 的增长速度和各区使用率，再结合 GC 日志看每次的触发原因和回收效果。Young GC 频繁，多半是分配速度太快，比如循环里创建大量临时对象，或者新生代太小；Full GC 频繁，就看老年代回收后的水位：一路上涨是内存泄漏，要做类直方图或堆转储找原因；不涨但很快又满，可能是新生代太小导致对象过早晋升、大对象太多，或者元空间不够、代码里调用了 System.gc()。定位后优先改代码，再考虑调整新生代大小或换收集器。
线上 OOM 或者内存泄漏怎么排查？
先看 OOM 的提示，确认是堆、元空间、直接内存还是线程数的问题。如果是堆，用 jstat 或 GC 日志看老年代在 GC 后的水位，正常是锯齿形，泄漏是一路上涨；然后取证，两次类直方图对比看哪个类在涨，或者用 HeapDumpOnOutOfMemoryError 保留的堆转储，用 MAT 看 Dominator Tree 找占内存最多的对象，再看 Path to GC Roots 找谁引用着它。常见原因是静态集合当缓存没淘汰、ThreadLocal 没 remove、资源没关闭。生产环境 dump 堆会停顿、文件大、含敏感数据，最好先摘流量。
JVM 调优一般从哪些方面入手？
我会先确认问题是不是真的出在 GC，用 GC 日志和 jstat 看频率、停顿和回收后的水位，大多数时候根因在代码，比如泄漏或者创建了过多临时对象。确认是 GC 问题后，先明确目标是吞吐、停顿还是内存，再调整：堆大小设成固定值、容器里给堆外内存留足空间；按延迟要求选收集器，一般服务用 G1 设停顿目标，延迟敏感的大堆用 ZGC；新生代太小导致过早晋升就调大新生代。每次只改一个参数，在相同压力下对比指标。

自测

  1. jstat -gcutil 输出里，O、YGC、FGC 列分别是什么？怎么从中看出内存泄漏？
    O 是老年代使用率（%），YGC 是 Young GC 次数，FGC 是 Full GC 次数。泄漏的信号是老年代在 GC 之后的使用率一路上涨、降不下来，最后 FGC 次数猛增。LeakDemo 实测 O 从 34% 涨到 99.9%，FGC 在最后几秒从 1 次变成 16 次，随后 OOM。
  2. 读一下这行日志：GC(0) Pause Young (Normal) (G1 Evacuation Pause) 110M->111M(2048M) 16.331ms。
    第 0 次 GC，是一次普通的 G1 Young GC，原因是 Eden 满了需要疏散活对象；GC 前堆用了 110M，GC 后 111M（刚启动时对象基本都活着，GC 期间又有新分配），堆总大小 2048M；停顿了 16.331 毫秒。
  3. CPU 飙高时，怎么从进程一路定位到具体的代码行？
    top 找到 CPU 最高的 Java 进程；top -Hp <pid> 找到最忙的线程号；printf '%x' 转成十六进制；在 jstack <pid> 输出里找 nid=0x... 对应的线程，看栈顶的代码行，多打几次确认。JDK 11 起也可以隔几秒打两次 jstack，比较每个线程的 cpu=，涨得最快的就是它。
  4. Young GC 频繁和 Full GC 频繁，分别该往哪些方向查？
    Young GC 频繁：对象分配太快或新生代太小，先找代码里大量创建临时对象的地方（循环拼字符串、反复装箱、大查询结果），再考虑增大新生代。Full GC 频繁：看老年代在 GC 后的水位，一路上涨是内存泄漏，做类直方图或堆转储；不涨但很快又满，查新生代太小导致的过早晋升、大对象、元空间不足，以及代码里的 System.gc()。
  5. 堆转储和线程转储有什么区别？生产环境转储堆要注意什么？
    线程转储（jstack、kill -3）记录所有线程此刻的状态和调用栈，很小、很快，用来查卡死、死锁、CPU 高；堆转储（jmap -dump、jcmd GC.heap_dump）记录堆里所有对象，用来查内存问题。转储堆时进程会停顿，文件和堆使用量差不多大，可能包含用户数据，要先确认磁盘空间，最好先摘掉流量。
  6. 用 MAT 分析内存泄漏时，主要看哪几样东西？
    Histogram 看哪个类的实例最多、占内存最多；Dominator Tree 看哪个对象“支配”了最多的内存，也就是它被回收就能释放多少；对可疑对象查 Path to GC Roots，找出是谁一直引用着它，定位到具体的字段和代码。
  7. Java 进程的内存为什么会比 -Xmx 大很多？容器里 -Xmx 该怎么设？
    -Xmx 只限制堆。进程还有元空间、线程栈、代码缓存、GC 自己的数据结构、直接内存和本地库的内存。实测 256MB 堆的进程，GC 数据结构占 54MB，线程栈占 48MB。所以容器里 -Xmx 一般设成容器内存的 70% 到 75%，或用 -XX:MaxRAMPercentage=75.0，给堆外留出空间。
  8. 为什么不建议一上来就调 JVM 参数？
    大多数性能和内存问题的根因在代码（泄漏、过多临时对象、过大的查询结果），调参只能掩盖。应先用 GC 日志、jstat 等数据确认确实是 GC 问题，明确要优化的是吞吐、停顿还是内存，再一次只改一个参数，在相同压力下对比效果。
